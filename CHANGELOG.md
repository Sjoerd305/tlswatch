# Changelog

Newest first, one line per change.

## Unreleased

- CI runs gosec 2.30.0. The pinned 2.29.0 cannot read the export data of Go 1.27 packages and had analysed nothing since the Go 1.27.3 build, passing quietly. Under the new rules the theme cookie is HttpOnly like every other cookie (no script read it), the single sign-on state is cleared with the SameSite it was set with, an SCT timestamp with its top bit set no longer counts as an issuance date, and list limits are bound as parameters.

## v0.1.2 — 2026-10-22

- Built with Go 1.27.3, whose certificate verifier refuses chains through the eight compromised eMudhra intermediates (EM DV/OV/EV TLS CA - G3B and - G3C, EM OV CS CA - G3B and - G3C, blocked by their key, so the cross-signs under AAA Certificate Services too). A target served through one of them now reports `chain_untrusted` instead of passing. The build image is pinned to `golang:1.27.3-alpine`.
- Distrust calendar: Mozilla's removal of emSign ECC Root CA - G3 from NSS on 20 October 2026 and Chrome's from its root store on 27 October 2026, after eight of eMudhra's intermediates had their keys compromised. Certificates under that root report `distrusted_ca`, a warning for Chrome until the 27th and critical for Mozilla already. The root no longer counts as trusted by either program for cross-signs. `DistrustTable` is 2.
- Filter chip counts follow the other filters. On Targets, Domains, Certificates and the domain page, each chip counts the rows it would show under the filter text and the other groups' active chips, updated live as filters change; a chip that would show nothing is dimmed with a count of 0.
- No instance is indexed by search engines: every response carries `X-Robots-Tag: noindex, nofollow`, and a demo also serves a `robots.txt` that disallows all crawling.

## v0.1.1 — 2026-10-19

- A node's allowlist shows on the server. Nodes report their allowlist of CIDRs, the local-address switch and where they were set with their system facts; the node page shows them read-only under Probe limits with where to change them on that machine (`/etc/tlswatch-node.env` and a restart, the `-allow` flag, or the container's environment), and the nodes list tags a node with an allowlist. A changed allowlist is audited. The install script writes `TLSWATCH_NODE_ALLOW` and `TLSWATCH_NODE_ALLOW_LOCAL` commented out in the environment file. A node shows "Not reported" until it is updated.
- REST API and import/export. Under Account a user makes API tokens (name, a role no higher than their own, 30 days to a year, or no expiry for admins), shown once and stored hashed; a token acts with the lower of its role and its user's, is deleted when its user is disabled or deleted, and is rate limited. The public API under `/api/v2` takes only those tokens, never the session cookie: targets (list with the page's filters, get, add, change, delete, check now), certificates, findings (list, get, acknowledge), domain watches (list, get, add, change, delete, poll now), issuances, channels (list, test; admin) and the export. Lists are paginated with a cursor, errors are JSON with a stable code, and every write is audited with the token's name. `GET /api/v2/openapi.json` is generated from the same endpoint table and served without sign-in. Settings › Export downloads the targets and domain watches as YAML with only the non-default settings, channels, bundles and nodes by name and no credentials; Targets › Add many takes that document back (pasted or as a file) and shows what it adds, changes and leaves out before one all-or-nothing import, removing what is absent only when asked. Add many also takes CSV with the columns of its line format. Schema migration 21 adds the token table; a restore deletes the tokens of the backup. New dependency: `go.yaml.in/yaml/v3`.
- Two-factor sign-in and generic OpenID Connect. A local account sets up TOTP under Account by scanning a QR code (drawn on the server as SVG, no library) and confirming a code; it gets 10 single-use recovery codes, shown once and stored hashed, and the secret is sealed under the secret key. Sign-in then asks for the code after the password; a code is accepted once, and a wrong one counts towards the lockout like a wrong password. Settings › Sign-in requires TOTP per role: such an account sets it up before it can open anything else. Admins reset a user's TOTP under Users; enabling, turning off, resetting, new recovery codes and recovery-code sign-ins are audited. Next to Google, one OpenID Connect provider (Entra ID, Keycloak, Authentik, Okta, …) is configured by issuer URL through discovery, with client ID and secret, scopes, an allowed e-mail domain, and an optional role claim that maps groups to roles at every sign-in and can create users. Google is now a preset of the same implementation. Users get the login method `oidc` (schema migration 20 rebuilds the users table); `rotate-key`, backups and restores re-seal the TOTP secrets.
- Three more channel kinds and a calendar feed. Microsoft Teams posts an Adaptive Card to a Workflows webhook; Matrix sends a notice into a room through the client-server API, idempotent across retries; PagerDuty opens one incident per finding through the Events API v2, triggered on open, escalation and reminder and resolved on recovery, with the finding as dedup key. Alerts to PagerDuty are never batched: the outbox now passes a lone alert's event and finding to the transport. Under Account, a user creates a secret ICS feed (all targets or one tag) with an all-day event per served certificate on its expiry date and one on the renewal point of renewal-managed targets; renewals move the events. Feed tokens are stored hashed, shown once, revocable and audited.
- Post-quantum key exchange. Every handshake records the key exchange group it negotiated, and the daily configuration test adds one handshake at TLS 1.3 offering only X25519MLKEM768. The result is a grade reason, "post-quantum key exchange: yes" or "no", that does not change the letter. The grade rules move to version 2 for it, so every target takes the configuration test on its next check after the upgrade. The targets list gets PQ chips (yes, no, untested), the overview a line "12 of 40 targets negotiate post-quantum key exchange", `/metrics` `tlswatch_targets_pq{state}`, and `tlswatch check` `pq_kex` and `key_exchange_group` per address. Nodes need an update to test it; until then their targets show as untested.
- CAA monitoring. Every CT poll looks up the watched domain's CAA record set (climbing to the parents as RFC 8659 prescribes, through the system's name servers) and stores it; a changed set is an info event `caa_changed` under recent changes. Each new issuance is judged against it, per name and with `issuewild` for wildcards, using a table of the CAs' CAA identifiers; one the record does not allow opens a new warning `caa_violation` on the watch, acknowledged like an unexpected certificate. An issuer the table does not know is shown as "CAA not evaluated". The domain page shows the current record, or that any CA may issue.
- A certificate change says what changed. The `certificate_changed` warning, its alert and the renewal event under recent changes carry a one-line diff of the old and new leaf: issuer, a replaced intermediate, subject, SANs added and removed, key, signature algorithm, expiry and lifetime, unchanged fields left out ("SANs +api.example.nl −old.example.nl; key RSA 2048 → ECDSA P-256; lifetime 90 → 47 days"). A renewal from the ACME CA that no longer covers the target's server name is a warning, not a routine renewal.
- Revocation through CRLs. Before the checks, the CRL each served leaf names is fetched at most once a day per URL, verified against the leaf's issuer from the chain (partitions by their distribution point; delta CRLs, replayed older copies and CRLs over 50 MB are refused) and cached with its serials. A new critical finding `revoked` opens when the leaf is listed, or when the server staples an OCSP response saying so; it stays until a different leaf is served. `revocation_unknown` (info, never alerted) is recorded when a CRL could not be checked on 3 days in a row; a leaf without a CRL records nothing. The CRL of a private CA on a node target with a CA bundle is fetched by the node with the new `crl` job kind and verified on the server. The probe records the stapled OCSP response; a good one is a grade reason, "OCSP stapled", that never lowers the grade. The target page shows a Revocation row. Nodes must be updated to fetch CRLs.

## v0.1.0 — 2026-10-18

- Discovery. Targets › Discover scans private address ranges (at most a /20 and 16 ports per scan, 50 connects per second by default) from this server or from a node, with the new `scan` job kind, and lists every TLS endpoint it finds with its certificate and the target that already covers it. "Add selected" opens Add many pre-filled, with the certificate's name as server name where it resolves to the address. Scans are audited, kept 7 days and are not inventory; public ranges need Settings › General › "Allow discovery of public addresses". The domain page lists "Names without a target" from the known certificates of the last 90 days, and an unexpected certificate offers "Add as target". Add many lines take `protocol=` and `sni=`. Nodes report the job kinds they run and answer an unknown kind at once; a node must be updated before it can scan.
- Distrust calendar: a new finding `distrusted_ca` reports a certificate whose chain is anchored in a root a root program distrusts or has removed. It is a warning while the distrust is ahead and critical from the day it takes effect. The table in the binary covers the distrusts of Entrust (with AffirmTrust), Chunghwa Telecom, NetLock and GLOBALTRUST by Chrome, Mozilla, Apple and Microsoft, Apple's of Camerfirma and ComSign, and the root removals by Chrome and Mozilla, among them the DigiCert G1 roots and Mozilla's 2027 batch. Chrome judges by the embedded SCT, the others by NotBefore. A cross-sign from an old root next to a root the browser still trusts is not reported. The chain view names the event and links the announcement; Certificates gets a Distrusted chip; the digest lists the events of the next 90 days with the targets they will affect.
- Expiry thresholds follow the certificate's lifetime, for the 200-, 100- and 47-day caps and 6-day certificates. Warning and critical each take days and a share of the lifetime left, and fire once both have passed: long-lived certificates keep their day thresholds, short-lived ones scale (a 6-day certificate warns at about 29 hours, not at issuance). The defaults are 30 d and 33 %, 7 d and 10 % for manual renewal, and 10 d and 20 %, 3 d and 7 % for renewal managed. Targets keep their own day values and take the percentages from the defaults; 0 on a target, or an empty field in Settings › Defaults, means days only.
- New warning `renewal_overdue`: a renewal-managed target still serves a leaf past its renewal point (75 % of the lifetime by default, 50 to 95 % per target), so a renewal that ran and was never deployed, or an ACME client that stopped, shows up while there is time. While it is open, a warning-level `expiring` is not alerted or reminded on its own; the escalation to critical still is.
- Time left is shown in hours under a week ("expires in 31 h"), in the UI and in alerts. A target checked less often than a fifth of its certificate's lifetime gets a note on its page. "Expiring next" and the digest rank by the share of the lifetime left when lifetimes differ by more than a factor of four.

## v0.0.6 — 2026-10-17

- Behaviour tests across every package, written against the specification; everything they found is fixed:
  - Checks: a certificate that is not valid yet opens a new critical `not_yet_valid` finding (it passed as healthy); a weak RSA key on a root the server sends opens `weak_signature`; an expired root sent needlessly after a valid chain is no longer critical and the chain view says it can be dropped; a self-signed certificate put in the target's own bundle is trusted; an IPv6-only name without an IPv6 route says so.
  - Targets: one address of several down makes the target a warning, with the failing addresses on its page and in the digest (it stayed healthy); a balancer member coming and going no longer opens `certificate_changed`, nor does a new host or port; a target stays editable while its node re-enrols; IP addresses are stored in one spelling and Unicode host names as punycode; an unknown CA bundle is a form error.
  - Alerts: recovery reaches every channel that was told about a finding, also after the retention and when added later; escalation ends an acknowledgement; the weekly digest is never merged into an alert batch and is sent within a day when its hour was missed; a mention in a target name never pings a Mattermost, Rocket.Chat or Telegram chat; SMTP delivers per recipient, does not retry a 5xx and no longer resends mail the relay accepted when QUIT fails.
  - Certificate Transparency: an issuance that expires while pending closes silently; Mark unexpected sticks; crt.sh issuer names with quoted commas and unparsable Cert Spotter entries are read.
  - Nodes: a node that cannot update no longer polls in a tight loop; a job of a node gone offline mid-job no longer hangs its check; "updating 2 of 5" counts the round; facts sent too soon are sent again; `TLSWATCH_NODE_*` booleans take `1` and `yes`, and a bad value or stray argument stops the node.
  - Every HTTP channel fails an alert at once on a client error (a deleted webhook, a revoked token) instead of retrying it hourly for a day; server errors, timeouts and rate limits are still retried. A Telegram chat that does not exist no longer holds up the others.
  - Follow-ups: a recipient or chat refused for good stays named on the alert ("not delivered to …") after a retry reaches the others, and the channel shows "partly"; a retry carries the reference of the first attempt, so receivers can de-duplicate; ntfy messages are cut at 4000 bytes instead of characters; an alert names failing addresses in address order; the digest marks an expiry critical by the target's own threshold; Add many adds all lines in one transaction; enabling a domain watch again reopens its unexpected issuances; a Cert Spotter entry without its certificate keeps the issuer CN instead of the whole DN; an IPv6 address as target gets its own "no IPv6 route" message; an offline node counts only enabled targets as waiting; Reject cannot undo a Confirm made at the same moment; a cancelled node job keeps its pool slot until the node answers.
  - Found on a live instance: an expired root from the trust store is reported as `expired`, naming the root, instead of `chain_untrusted` with a date from 2020; a node reinstalled by hand no longer keeps showing "update failed"; Update and Update all are offered only for nodes the server has a binary for (on a development build, only its own platform, with `-allow-unsigned-update` on the node); link-local addresses coming and going no longer write a `node.facts` audit entry every hour.
  - Web and settings: switching a user to Google ends their sessions and password links; a field set by the environment is no longer written to the database on save, and metrics switched on by the environment get a token; bulk edit saves in one transaction and a shorter interval takes effect at once; the PEM download name is sanitised; Sign out after the session ended goes to the sign-in page; a backup with data after its end, or asking for more than 256 MiB of key memory, is refused; `tlswatch check -h` exits 0.
- Fix: on the targets list, long names, hosts, node names or several tags could push the Check button out of sight. Long text is cut with an ellipsis (whole on hover), and a table that still does not fit scrolls sideways with the Check button pinned to the right.

## v0.0.5 — 2026-10-16

- Security review of the whole codebase; everything it found is fixed in this release:
  - Nodes replace their binary only with a release whose `SHA256SUMS` is signed by the tlswatch release key (built into every binary; releases now publish `SHA256SUMS.sig`). A server, or anyone who could edit a GitHub release, can no longer hand a node a binary of its own. The server serves its own executable only when it is the released one and otherwise sends the node to the release asset. New node switches `-no-self-update` and `-allow-unsigned-update` (for development builds); a node on `-insecure` never updates. The manual install command verifies the checksum too.
  - `/metrics` requires a bearer token, generated when metrics are enabled and shown under Settings › General (or `TLSWATCH_METRICS_TOKEN`): the metrics name every target and its weak configurations.
  - Fix: `?next=` on the sign-in page could redirect to another site through an embedded tab character. Redirects now go only to a parsed path on this origin.
  - Fix: twenty failed requests from an address blocked valid nodes behind the same address (a reverse proxy, a NAT) for 15 minutes. The credential is checked first; the block applies to requests without a valid one.
  - Fix: `tlswatch rotate-key` and a restore left the Cert Spotter API key (and unspent node install tokens) under the old key, silently losing it. Every sealed value is re-sealed, and a Google secret or CT key that cannot be read is shown as such on its settings page.
  - A server that finds its database but not its key file refuses to start instead of generating a new key (`TLSWATCH_ACCEPT_NEW_KEY=true` overrides); a key file readable by others is reported.
  - Session and CSRF cookies carry the `__Host-` prefix over HTTPS; requests a browser marks cross-site are refused outright; HSTS covers subdomains; the embedded static files no longer list their directories.
  - The lock after failed sign-ins holds for the last good address too from 25 failures in a row, and the count is kept in one statement; the sign-in address is matched case-insensitively.
  - The setup form answers "already set up" before hashing a password; the restore form checks its token as soon as it arrives and reads a bounded number of parts.
  - The audit log is kept for at least a year whatever the history retention; acknowledging a finding a check resolved meanwhile no longer reopens it; a restore drops one-time invite links as well as sessions; the database, its copies and `tlswatch backup` files are created owner-only.
  - What a node reports (hostname, system, interfaces, version, error) is bounded and stored at most once per five minutes; a node's result is parsed outside the dispatcher's lock.
  - Discord messages are posted with mentions off; channel posts follow no redirect; an issuance keeps at most 100 names and a finding lists a dozen; a panic in a check is logged and the process goes on; failed checksum fetches are not retried per request; the audit log search escapes `%` and `_`.
  - The server verifies every chain a node reports itself, under system trust as under a bundle, so a node can say what it saw but not what to trust. The binary download takes a node credential or an unspent install token. Sealed values are bound to their place in the database. `Permissions-Policy` and cross-origin opener and resource policies are set; `/healthz` no longer names the version; a fresh install behind a TLS proxy gets Secure cookies before the proxy trust is configured; `create-admin` shows the link on the terminal or writes it to a file (`-out`); a failed backup migration is logged, not shown.
  - CI: actions and base images pinned by digest, the release jobs hold only the scope each needs, scan tools pinned; SQLite keeps temporary data in memory, since the image has no `/tmp`; the Dockerfile and the release build use the same flags.

## v0.0.4 — 2026-10-16

- Certificate Transparency polls are gentler on the free sources: watches are polled one at a time, two seconds apart, and spread over the interval instead of coming due together; a failed poll (crt.sh answers 502 when it is busy) is retried after 15 minutes, or after what a 429 asked for, instead of at the next interval.
- Fix: after the upgrade, Check all and the scheduled checks left targets without a grade until their next daily configuration test. A target without a grade, or graded under older rules, now runs the test on its next check.
- Fix: the "log entry" link of an issuance found through Cert Spotter opened a page that does not exist. It now opens the certificate on crt.sh by its SHA-256; links stored by the previous build are replaced by the domain's crt.sh listing.
- Certificate Transparency watching. **Domains** in the navigation lists the domain watches: a registrable name, with subdomains by default, tags, channels and notes. Every enabled watch is polled hourly (Settings › Certificate Transparency: Cert Spotter by default with an optional API key, or crt.sh; the interval from 15 minutes to a day; a Test button; and one sentence that says what leaves the server, which is the watched names and nothing else) for the certificates publicly issued for it. An issuance is matched to the inventory by issuer and serial: `known` when a target serves it, `pending` for 48 hours when its names are covered by an enabled target with the same issuer (a renewal on its way), and otherwise `unexpected`, which opens an `unexpected_certificate` warning on the watch with the names, the issuer, the date and a link to the log entry. A served renewal becomes known and is recorded as a quiet `certificate_issued` change; an unexpected one a target serves later resolves with a recovery notice; acknowledging resolves it and the issuance keeps who and why; a known issuance can be marked unexpected by hand; an expired one closes silently. A new watch's first poll records the last 90 days as known without findings. A source that answers nothing for a day opens `ct_source_failed`, resolved by the next successful poll. The domain page lists the issuances with state chips, the matched target and the log entry; the findings page shows the watch as the subject; the digest gets "Issued for your domains this week"; `/metrics` gains `tlswatch_ct_issuances_total{state}` and `tlswatch_ct_last_poll_timestamp_seconds{domain}`. Watches are audited, in the backup, and their issuances follow the retention. The findings table is rebuilt once by the migration.
- A TLS configuration grade per target, A to F. The daily test for TLS 1.0 and 1.1 (now "Configuration test" on the target form) also offers four weak cipher suite classes on their own, one pinned TLS 1.2 handshake each: RC4, 3DES, RSA key exchange without forward secrecy, and CBC with SHA-1. Every address is graded from what it accepted, the chain's keys and signatures, and its highest version (TLS 1.2 without 1.3 is a B); the target's grade is its lowest address, and every grade carries its reasons. Certificate validity stays out of the grade. A new `weak_configuration` warning opens for RC4, 3DES and no forward secrecy (CBC and a missing TLS 1.3 lower the grade without a finding); a changed grade is recorded under recent changes and in the target's findings as an info event, and the weekly digest lists the grades that dropped. The targets list has a sortable grade column and grade chips, the target page shows the grade with its reasons and the per-address result of the test, Test without saving shows it too, and `tlswatch check` reports `grade`, `grade_reasons` and `weak_suites_accepted` per address (`-no-config-test` skips the test; `-no-legacy` stays as an alias) and exits 1 for a C or F. `/metrics` gains `tlswatch_targets_by_grade` and `tlswatch_target_grade`. Nodes run the same handshakes; the grade is computed on the server, under a versioned rules table stored with each grade.
- The overview's "Expiring next" shows ten targets and folds the rest behind "Show all N"; a second click folds them again.

- Targets in bulk. "Add many" on the targets page takes one host per line (a host, `host:port` or a URL, with an optional name after it) and the settings they share, and adds them all at once; a bad line holds the whole list back and is named by line number, a host that already exists is skipped. Every row on the targets list has a checkbox; "Edit settings" on the selection bar opens one form for the selected targets, where tags are added or removed, checks enabled or disabled, and any other setting (node, trust, renewal, thresholds, interval, probe settings, reminders, channels, notes) is written only when its "change" box is ticked. Both are audited per target with `bulk=true`.
- The overview's "Expiring next" lists every enabled target that serves a certificate, soonest first; it stopped at eight.
- One layout across the pages: every page is at most 1680px wide (Targets was, the rest stopped at 1400px), and every form is at most 760px wide, where before Add target was 1352px wide and shrank to 680px when the test result appeared beside it, settings forms were 1152px and Account 680px. Smaller things from the same pass: the filter field is 300px on every list (Targets and Findings had 260px), the lifetime bar on the overview is the same 110px as in the lists, and an empty state with a title is centred on the settings pages as it is on Targets and Certificates.
- Targets list: a row's tags stay on one line. Up to three are shown; with more, the first two and a "+N" tag that lists the rest on hover. Before, the tags column was squeezed to its widest tag, so several tags stacked into a ragged column, and the table was wider than the page, so its right edge (tags, last check, Check) was cut off. - Filter chips on Targets, Certificates and Findings flow on one wrapping line: before, a chip group that did not fit (tags, once node chips were added) dropped to the next line as a whole, leaving a stray divider and a ragged edge.
- `tlswatch seed` is gone: demo data does not belong in the production binary. Add targets under Targets › Add target. `make run` starts an empty throw-away instance.
- Nodes use less data: the long-poll is held for up to 55 seconds instead of 30, so an idle node sends about half as many requests (a node is marked offline after 165 seconds without one instead of 90), and results and facts go up gzipped once the server says it accepts that. A proxy in front of the server needs a read and idle timeout of at least 60 seconds.

## v0.0.2 — 2026-10-16

- Releases add 32-bit ARMv7 (`linux/arm`, for Raspberry Pi 2 and 3 and many appliances) and Intel Macs (`darwin/amd64`) to the binaries, and `linux/arm/v7` to the Docker image. The install script recognises `armv7l` and refuses ARMv6 by name. The image is now cross-compiled instead of built under emulation, so a multi-platform build takes a fraction of the time.
- Nodes: probe from inside a network the server cannot reach. A node is the same binary run as `tlswatch node`; it connects out to the server over HTTPS (a long-poll, no WebSocket), runs the probes it is given and sends the results back, while the schedule, the inventory, the findings and the alerts stay on the server. Settings › Nodes › Add node shows one install command (and Docker and manual variants), watches the machine enrol, and shows its hostname, system and addresses for an admin to confirm. The target form gains "Probe from", the targets list a node column and chips, and a target whose node is offline shows "Waiting for node" instead of opening findings: one `node_offline` finding per node opens after 10 minutes. CA bundles stay on the server, which verifies bundle chains itself. Nodes update themselves to the server's version one at a time with rollback (automatic for release builds; containers are pulled instead), can be limited to an allowlist of CIDRs, and are removed with `tlswatch node uninstall` or the uninstall script the server serves. The migration rebuilds the findings table once.
- Every build names its commit. `docker compose up --build` no longer reports `dev`: the version is derived from the checkout by `scripts/version.sh`, which the Makefile and the Dockerfile share, so an image and a `make build` of the same commit print the same thing (`2026.10.15-5efacf7` while there is no tag, `v0.2.0-5-g5efacf7` past one, `v0.2.0` on one, `-dirty` for uncommitted changes). The `.git` directory is in the Docker build context for this.
- Sortable lists: every column head on Targets, Certificates and Findings sorts the list, a second click reverses it, and the order is part of the URL so a reload, a shared link and the live refresh keep it (also without JavaScript). Findings can be grouped by kind, like targets by tag. On phones the main lists are compact cards (status, name, host, days) instead of one labelled line per column. Smaller things from the same pass: the Healthy tile's "due within 30 days" counted expired and critical targets too; the "0 changed" tail on the Warning tile is gone; the reminder to set the public URL shows on the overview only; above eight issuers the certificate chips become a select; the theme can be switched from the account menu; the threshold placeholders on the target form read "30 manual · 10 managed"; the bundle field shows only for the CA bundle trust mode; the filter field shows its "/" shortcut; the expand control on the certificates page is a wider chevron; and row notes such as "2 addr", "smtp", "auto" and "pinned" are small tags.
- Four more channel types under Settings › Channels, next to SMTP and Telegram: **Slack** (an incoming webhook; Mattermost and Rocket.Chat incoming webhooks take the same message), **Discord** (a channel webhook), **ntfy** (a topic on ntfy.sh or your own server, with the severity as the ntfy priority and an optional access token) and a generic **Webhook** (a JSON POST with source, ref, severity, subject, text and sent_at, optionally signed with HMAC-SHA256 in `X-TLSWatch-Signature`). Webhook URLs that grant posting rights are stored encrypted like passwords and never shown back. Rate limits (429 with Retry-After) postpone the retry as Telegram's do. The channels table in the database is rebuilt once by the migration, so the first start after the upgrade takes a moment longer; nothing in it changes.
- Legacy TLS versions: every target is now tested once a day for whether it still accepts TLS 1.0 or TLS 1.1, with a handshake pinned to each version, and a new `legacy_protocol` warning opens while it does. Before, only the negotiated (highest) version was shown, so a server on TLS 1.3 that also accepted TLS 1.0 looked clean. The result is shown on the target page and in Test without saving; Check now always tests. The test can be switched off per target under Probe and reminder settings. `tlswatch check` tests too (`-no-legacy` to skip) and reports `legacy_accepted` per address, so a server accepting TLS 1.0 now exits 1. `tlswatch seed` adds tls-v1-0.badssl.com:1010.
- Backup and restore in the UI. Settings › Backup downloads the whole instance as one file encrypted with a passphrase, and restores such a file, or a `tlswatch backup` copy, in place while tlswatch runs; checks and alert delivery pause meanwhile and everyone signs in again afterwards. The setup screen of a new installation restores a backup too, without first creating an admin. Stored credentials are re-encrypted for the instance that restores, so a backup moves between hosts without the secret key file.
- Alert, digest and test mails now carry an HTML part in the style of the UI next to the plain text: status pill, countdown, the fields as a table with mono identifiers, and a button to open tlswatch; dark mode where the mail client supports it. Telegram stays plain text. Alerts queued before the upgrade go out as plain text.
- Without a release version, `tlswatch version` and the asset URLs use the git revision the binary was built from. Static files are cached for good unless the build is a development one (no version, or a modified working tree).
- Settings pages show validation messages and log any other error instead of showing its text.
- Prometheus metrics at `/metrics`, off by default: switch them on under Settings › General (or `TLSWATCH_METRICS=true`). They cover targets by status, open findings, the outbox, every target's certificate expiry and the scheduler.
- Settings › Defaults refuses text in a number field instead of saving it as 0. The findings page says "latest 1000 resolved" when the list is capped.
- `tlswatch rotate-key` replaces the secret key: stored credentials are re-encrypted under a new key, and the old key file is kept next to the new one.
- Each delivered alert records the reference it went out under: the SMTP Message-ID, or Telegram's message ID per chat. It is shown on the alert in the finding's timeline, so a message can be traced in the mail relay's logs or the chat.
- Every check logs what it changed: the check ID, the status, the findings opened, escalated and resolved, failures held back by the debounce, alerts queued and alerts held back by a channel's severity floor. See "Why did (or didn't) an alert go out?" in docs/operations.md.
- Database errors are no longer shown as "not found" pages or as raw text: they are logged and answered with a 500, and only messages meant for the user are shown. The overview's 24-hour summary and the navigation counts no longer hide query errors.
- Sign-in: an e-mail address without an account now locks after five failures exactly like one with an account, so the lockout no longer reveals which addresses exist. The lockout no longer applies to the address an account last signed in from, so failed attempts from elsewhere cannot keep its owner out.
- STARTTLS: a server may send at most 4 KiB per line and 100 lines per reply before the handshake.
- Operations: every response has an `X-Request-ID` that its log lines repeat; failed and slow requests are logged at info level. `tlswatch healthcheck` checks a running server, and the Docker image uses it as its health check. Shutdown waits for running checks and alert deliveries, and a delivery interrupted by shutdown still records that it was sent. `tlswatch backup` no longer migrates the database it copies. Checks started from the UI after adding, changing or enabling a target run through the worker pool.
- Faster pages as history grows. Each target records the check behind its current state, so the Certificates page, a target's page and the navigation counts no longer run a subquery per stored observation. The Certificates page loads a certificate's chain when its row is opened instead of up to 300 chains per render. The live-page poll reads one change counter instead of aggregating the findings and alerts tables. The hourly retention deletes in batches of 5,000 rows and finds unused certificates in one pass, so checks and sign-ins are not held up behind it. New indexes cover per-target findings and per-channel alerts.
- Static files are served under the release version (`/static/<version>/…`) and cached for good, so a browser never pairs a new `app.js` with an old `common.js` after an upgrade.
- Request bodies are capped at 1 MB (3 MB for CA bundle uploads) before anything reads them, also for signed-out requests; a larger request gets a 413. The 2 MB limit on bundle files now actually applies.
- Fix: deleting a CA bundle while a target using it was being saved could leave that target with an empty trust store, so every check reported an untrusted chain. The in-use check and the delete are now one statement, and a missing bundle is an error in the log instead of an empty trust store.
- Fix: a certificate restricted to client authentication was reported as trusted. Chains are now verified for server authentication, as a browser does; such a certificate raises `chain_untrusted`.
- Fix: when one chat of a Telegram channel failed, every retry sent the alert again to the chats that already had it. Each chat is now tried, the ones reached are remembered, and a retry goes only to the rest. Telegram's `retry_after` on rate limits is honoured.
- Environment overrides are validated like the UI fields. An invalid value (for example `TLSWATCH_RETENTION_DAYS=1`, `TLSWATCH_BEHIND_PROXY=yes`, an unreadable secret file) stops tlswatch at start with a message naming the variable, instead of being ignored or, for the booleans, silently turning the setting off.
- Sessions: a database error while loading the session no longer signs the user out (the request gets a 503 and is logged). A session now also ends 7 days after sign-in, however active; expired sessions are pruned hourly. Static files are served without a session lookup. Panics are logged with their stack.
- Fix: a check that was running while its target was disabled, or moved to another host, port, protocol, server name or trust setting, is discarded. Before, it re-opened the findings that disabling resolved, or stored the old endpoint's certificate and raised a false certificate change on the next check.
- Fix: the scheduler's one-minute refresh no longer undoes Check all or the spread of overdue checks after a restart. A check that cannot be stored (for example a full disk) is retried after 1, 2, 4 … minutes, up to an hour, instead of straight away. `/healthz` reports `overdue_s` and answers 503 when a due check has waited more than an hour.
- Fix: a channel whose settings cannot be decrypted (for example after the secret key changed) no longer stops every check from being stored. It is marked on the Channels page, its alerts fail with a visible error, and the other channels keep working. Delivery logs name the channel ID and the alert IDs, and giving up after 24 hours is logged as an error.
- Change detection: an open certificate or issuer change is resolved without an acknowledgement only by an automatic renewal. A manually replaced certificate no longer resolves an open issuer change.
- Users without SMTP: when no SMTP channel is set up, the admin sets a new user's first password (or creates a link to pass on) and can set a new password for a local user later. With SMTP, users get an e-mailed invite link and choose their own password, as before.
- Live pages: Overview, Targets, a target, Certificates and Findings update themselves when checks land or findings change (every 4 s while checks run, otherwise every minute; paused in background tabs, never while you type or have unsaved input). The background polling does not extend the session idle timeout.
- Findings: acknowledge several at once (checkboxes and a bulk bar); filter by text and by target, linked from the target page.
- Users: locked-out accounts show as locked with an Unlock button; users can be deleted (not yourself, not the last admin); the audit log keeps their entries.
- Forms disable their buttons while they are sent, so slow actions such as a channel test cannot be sent twice. The "certificates no longer served" switch now works both ways and keeps the filters.
- UI: rows in lists are clickable as a whole (targets, overview, findings, channels, users, certificate and history tables); cmd/ctrl or middle click opens a new tab. Tags in the targets table filter the list; the findings panel has a close button and closes on Escape; "/" focuses the filter; past expiry dates show "expired" instead of negative days; deleting a channel or CA bundle asks first; Disable is no longer styled as a destructive action.
- Targets can be deleted from the target page and the edit form, after a confirmation page that shows what is removed.
- Target status is Unreachable as soon as a check reaches no address (the finding and alert stay debounced); a protocol that does not fit a well-known port gets a hint; the port follows the protocol in the target form and the SMTP encryption in the channel form.
- First-run setup screen: the first admin creates their own account and password in the browser; no setup link or seeding needed.
- First version: probing (TLS and STARTTLS), checks and findings, alerts on SMTP and Telegram, inventory, web UI with roles, Google sign-in, and configuration through the UI.

# Specification – tlswatch

This is the maintained specification of tlswatch: it describes how the tool behaves and is updated in the same change as the code, so the version of the code is the version of this document.

## Purpose and scope

The tool monitors the certificates that are actually served on a list of hostnames and IP addresses, judges whether they are valid, and alerts by e-mail, Telegram, Slack, Discord, Microsoft Teams, Matrix, ntfy, PagerDuty or a webhook before they expire or when something changes. It is a single self-hosted Go binary with a web UI, built for 10 to 100 endpoints in a small operations team but designed to scale to thousands.

In scope for version 1:

- Probing TLS endpoints by hostname or IP address, on any port, including STARTTLS protocols.
- Checking expiry (leaf and intermediates), chain of trust, hostname match, and signature strength, with self-signed and private-CA certificates as expected states.
- Detecting a changed certificate, with an exception for endpoints whose certificate is renewed automatically (Let's Encrypt and other ACME clients).
- A certificate inventory: every certificate seen, where it is served, when it expires.
- Alerts on SMTP, Telegram, Slack, Discord, Microsoft Teams, Matrix, ntfy, PagerDuty and generic webhooks, with reminders, recovery notices and acknowledgement, and an ICS calendar feed of the expiry dates.
- Users with the roles admin, operator and viewer; local login with an optional TOTP second factor, and single sign-on through Google or any OpenID Connect provider.
- A daily check per target by default, 180 days of history.
- A TLS configuration grade per target (A to F) from the protocol versions, cipher suites and key the server accepts, tested once a day next to the legacy TLS test.
- Certificate Transparency watching: every certificate publicly issued for a watched domain is matched against what the targets serve, and one that no target serves is reported.

Out of scope for version 1: certificate issuance or renewal, and uptime monitoring. A public REST API and the other features adopted after the competitive research that are not built yet are specified under Planned after version 1.

The tool does not manage certificates. It only observes what is served and reports on it.

## Terms and data model

The certificate is the primary entity; a target is where it is observed. One certificate served on many hosts is one record with many endpoints, which is what makes the inventory useful.

| Entity | What it is | Key fields |
| --- | --- | --- |
| Target | One endpoint to probe: a hostname or IP address, a port and a protocol | name, host, port, protocol, servername (SNI), trust mode, CA bundle, renewal managed (yes/no), expected issuer, thresholds (days and share of the lifetime), renewal point, interval, configuration test (on/off), tags, notes, channels, enabled, node |
| Observation | The result of one probe of one target at one resolved address | target, address, checked at, status, TLS version, cipher, key exchange group, leaf certificate, chain, stapled OCSP status, error, duration, node |
| CRL | The cached revocation list one or more served leaves name, fetched at most once a day (see Revocation) | URL, issuer key, this update, next update, fetched at, attempted at, failures in a row, last error, size, node, revoked serials with date and reason |
| Configuration test | The result of the daily test of one target at one address: which legacy versions and which weak cipher suite classes the server accepted, whether it negotiates post-quantum key exchange, and the grade that follows (see TLS configuration grade) | target, address, tested at, versions accepted, suite classes accepted, post-quantum key exchange, grade, reasons |
| Domain watch | A domain whose public certificate issuance is followed in Certificate Transparency logs (see Certificate Transparency watching) | name, subdomains included (yes/no), tags, notes, channels, enabled, last polled, cursor, CAA record set with where and when it was looked up |
| Issuance | One certificate for a watched domain as published in the logs | domain watch, issuer, serial, names, not before, not after, log entry, first seen, state (pending, known, unexpected, acknowledged), matched certificate, CAA verdict |
| Scan | A discovery scan of address ranges and ports, from the server or a node, with the TLS endpoints it found; kept 7 days, not inventory (see Discovery) | ranges, ports, rate, node, state, progress, endpoints found (address, port, protocol, TLS version, leaf subject, SANs, issuer, expiry), started by |
| Node | A probe worker inside another network, enrolled with the server and reached only by its own outbound connections (see Nodes) | name, state, credential hash, last seen, version, address, pool size, system facts, enabled, notes |
| Certificate | One X.509 certificate, keyed by SHA-256 fingerprint | fingerprint, subject, issuer, serial, not before, not after, SANs, key type and size, signature algorithm, PEM, first seen, last seen |
| Finding | A problem on a target, a node or a domain watch that is open until it resolves | target or node or domain watch, kind, severity, opened at, resolved at, acknowledged by and until, details |
| Alert | One delivery of a finding or recovery to one channel | finding, channel, sent at, result |
| Channel | A delivery route: an SMTP recipient list, a Telegram chat, a Slack, Discord or Teams webhook, a Matrix room, an ntfy topic, a PagerDuty service or a webhook URL | kind, settings, minimum severity |
| Calendar feed | A user's secret ICS URL of the expiry dates, optionally for one tag (see Alerting) | user, token hash, tag, created, last fetched |
| CA bundle | A PEM bundle of private roots and intermediates, uploaded by an admin | name, PEM, fingerprints |
| User | A person who signs in | e-mail, name, role, login method (local, Google, OpenID Connect), password hash, TOTP secret (sealed) with the time it was set up and the last step used, recovery code hashes, enabled |
| Audit entry | Who changed what in the tool itself (targets, users, settings, acknowledgements) | when, user, action, object, details |

A finding is opened when a check first fails and resolved when a later check passes. The same problem does not open twice; an alert fires on the transition, reminders on a schedule, a recovery notice on resolution.

## Targets and probing

A target is `host:port` plus a protocol. The host is a DNS name or an IPv4/IPv6 address; the port defaults from the protocol and can be anything. The host is stored in one spelling, so a repeat is found: lower case, without a trailing dot or brackets, an IP address in its canonical form (`2001:db8::1`), and an internationalised name in punycode (`bücher.example` is stored and probed as `xn--bcher-kva.example`, and the name defaults to the Unicode form). The server name is normalised the same way.

**Protocols**

| Protocol | Default port | Handshake |
| --- | --- | --- |
| `tls` | 443 | Implicit TLS on connect; covers HTTPS, SIP-TLS (5061), LDAPS (636), IMAPS, SMTPS, any custom port |
| `smtp` | 587 | STARTTLS after EHLO |
| `imap` | 143 | STARTTLS |
| `pop3` | 110 | STLS |
| `ftp` | 21 | AUTH TLS |
| `postgres` | 5432 | SSLRequest |

A STARTTLS server that stops offering STARTTLS is reported (`tls_unavailable`); this also catches STARTTLS stripping.

**Name versus address.** The server name sent in SNI and used for hostname verification is a separate field, `servername`, which defaults to the host when the host is a DNS name and is empty when the host is an IP. This allows probing `10.0.0.5:443` while verifying `portal.example.nl`, for a service behind a bastion or not yet in DNS. An IP target without a servername is checked for expiry and chain, not for hostname.

**Multiple addresses.** A DNS name may resolve to several A/AAAA records (a load balancer, anycast, dual-stack). The prober resolves the name at every check and probes every address, up to 8, in parallel. Each address yields its own observation. The target's status is the worst of its addresses: when some addresses answer and others cannot be reached, the target is at least a warning and its page names the failing addresses, but no `unreachable` opens (that needs all of them), and the digest lists it among the failed targets. A finding `inconsistent` opens when addresses serve different certificates. This catches the common failure where one node behind a balancer was never updated. Per target this can be set to "first address only". If the probing host has no IPv6 route, AAAA records are skipped and noted, not reported as unreachable. A name with only AAAA records is then unreachable from that host, and the error says so: the name has only IPv6 addresses and there is no IPv6 route, so probe it from a node with IPv6. For an IPv6 address as the target it says that this address is IPv6.

**Trust mode** per target:

- `system` (default): verify against the operating system's root store.
- `bundle`: verify against an uploaded CA bundle, for internal PKI.
- `self-signed`: no chain verification; the first observed fingerprint is pinned, and a different certificate later opens a `certificate_changed` finding.

**Scheduling.** Default interval is 24 hours; per target it can be lowered to a minimum of 1 hour. Checks are spread over the day with a per-target jitter so that a restart does not fire every probe at once. Operators can run "Check now" on a target. A worker pool (default 8 concurrent probes) with a 10-second connect timeout and 2 retries keeps a run of 1,000 targets under a few minutes.

**Network reach.** The tool probes from where it runs. Internal addresses must be reachable from that host; for isolated customer networks a node inside the network (see Nodes below) probes from there, or a route into the network makes the addresses reachable. Probes accept TLS 1.0 and up so that old appliances and embedded management interfaces can still be monitored; the negotiated version is recorded and shown. Accepting a version to read the certificate is separate from reporting that the server still offers it: see `legacy_protocol` and the TLS configuration grade below.

## Nodes: probing from inside another network

A node is the same binary started as `tlswatch node`, running on a host inside a network the server cannot reach. It holds no database, no settings and no schedule. It opens outbound HTTPS connections to the server, waits for probe jobs, performs each probe with the `internal/probe` package exactly as the server would, and sends the result back. The server keeps the schedule, the data, the checks and the alerts; a target is simply marked as probed from a node instead of from the server. To the rest of the application a node target is an ordinary target whose handshake happened elsewhere.

**Why a node and not something else.** A network route (a WireGuard or Tailscale subnet router, an SSH tunnel) needs no code and is the first thing to try when the customer allows a route in; the operations guide names it. A second instance works today but splits the inventory, the users and the alert rules. A cron job running `tlswatch check` and pushing JSON would move the schedule out of the UI, lose Check now and Test without saving, and give no node health; it is rejected. The node keeps one inventory and one schedule, and the customer network needs one outbound rule: HTTPS to the server.

**Transport.** The node is never connected to; every byte travels over a connection the node opened. It long-polls: `GET /agent/v1/jobs?wait=55s` is held open by the server until a job exists for this node or the ceiling passes, then answered with zero or more jobs; the node sends the next poll at once and runs the jobs in its own small pool. Results go up in a separate `POST /agent/v1/jobs/{id}/result`, so a slow handshake never delays the next command. The connection is kept alive between calls, so an idle node costs one small request and answer per ceiling and no new TLS handshake. Every poll answer carries `Accept-Encoding: gzip` (RFC 7694); a node that saw it on its last poll sends its results and facts gzipped (`Content-Encoding: gzip`), which shrinks the base64 chains, the more so when a host's addresses present the same chain. A server that does not advertise it gets plain bodies, so nodes and servers of different versions keep working. The server caps a body at 4 MB as sent and again after inflating. The held request is also the heartbeat: "last seen" is the time of the node's last request. A job that becomes due while the node's request is pending is delivered within one network round trip, so Check now from the UI reaches the node in milliseconds; the ceiling only decides when an empty answer goes out. A WebSocket was considered and rejected: on a link that carries one real message every half hour (daily checks spread by jitter), it would buy nothing measurable and cost a dependency, a reconnect state machine and an upgrade caveat for every reverse proxy in front of the server. The protocol is a set of commands and replies in its own package, with the transport behind a small interface, so a socket can replace the long-poll later without touching the messages.

| Setting | Value | Why |
| --- | --- | --- |
| Poll ceiling | 55 s | Under the common 60 s proxy and load-balancer timeouts (nginx `proxy_read_timeout`, AWS ALB idle), Cloudflare's 100 s and the server's own (write 150 s, idle 120 s); about two requests a minute from an idle node. The server holds a poll for the shorter of the node's `wait` and its own ceiling |
| Node client timeout | 70 s | A dead connection is noticed one hold after it breaks |
| Node offline | no request for 165 s | Three missed polls; Check now then fails fast instead of waiting |
| `node_offline` finding | offline 10 min | Rides out a reboot or an image pull without an alert |
| Jobs per poll | up to the node's pool size, default 4 | The server never leases more than the node can run |
| Reconnect backoff | 1 s doubling to 60 s | Reset on the first successful poll |
| Job timeout | target timeout × (retries + 1) + 30 s | After it the job is re-queued once, then given up as "no result from the node": the check is logged as failed, nothing is stored, and it is tried again after the scheduler's retry delay |

**Protocol** (`/agent/v1`, JSON, bearer credential, outside session authentication and CSRF, versioned in the path; a server refuses a protocol version it does not know):

| Call | Purpose |
| --- | --- |
| `GET /agent/v1/install/{token}` | The install script for one enrolment token, with the server URL and the token embedded; served without sign-in while the token is unspent and unexpired, otherwise 404 |
| `GET /agent/v1/uninstall` | The uninstall script; the same for every node, so it needs no token, and it works when the node's binary is gone or broken |
| `GET /agent/v1/download/{os}/{arch}` | The node binary: the server's own executable when the platform matches, else a redirect to the release asset of the server's version (a release build only); the SHA-256 in the `X-Tlswatch-Sha256` header either way |
| `POST /agent/v1/enrol` | Exchange a one-time enrolment token for the node's credential; carries the node's pool size and its system facts (see below). Rate limited per IP like sign-in |
| `GET /agent/v1/jobs?wait=55s` | The long-poll. Every call updates last seen, the node's version (`X-Tlswatch-Version`) and its address |
| `POST /agent/v1/facts` | The system facts, at every start of the node and then once an hour |
| `POST /agent/v1/jobs/{id}/result` | The result of one job; an unknown or expired job id is acknowledged and discarded |

A job is an envelope with an id and a kind. Version 1 has five kinds: `probe`, `cancel`, `update` (see Updating nodes), `scan` (see Discovery) and `crl` (see Revocation). A node lists the kinds it runs in its system facts; the server sends a node only those, and a node from before the list runs the first three. A node answers a kind it does not know with "unsupported kind" at once, so the server never waits out a job's timeout for it. A `cancel` goes out when the check waiting for a probe gives up; the probe keeps its place in the node's pool until the node answers or the job's timeout passes, so a node never runs more probes than its pool. The envelope exists so that later kinds (refresh a bundle, rotate the credential, report what a name resolves to from inside) need no new transport. A `probe` job carries the probe request without the Go-only fields: host, port, protocol, server name, trust mode, first-only, timeout, retries, allow-local, the legacy test flag, and the server's current time. The node resolves the host with its own resolver, so an internal or split-horizon name resolves as seen from inside the network; that, with reachability, is what the node is for. The node verifies with the server's time, so a node with a wrong clock does not produce false verdicts; the server stamps "checked at" itself when the result arrives. The result is the probe result with the chains as DER in base64: per address the TLS version, cipher, chain, verification outcome, hostname check, error kind and text, duration, the key exchange group, the legacy and post-quantum verdicts and the OCSP response the server stapled, plus the DNS error and the skipped IPv6 addresses. A pending or disabled node receives no jobs of any kind.

**CA bundles stay on the server.** Trust is managed in one place, Settings › CA bundles, and no bundle ever travels to a node. For trust mode `bundle` the node only captures the chain and the server verifies it against the bundle when the result arrives, so a replaced bundle takes effect on the next check of every node target without touching a node. For trust mode `system` the node verifies against its own operating system root store, which is what a network whose hosts already trust an internal root wants; when that store lacks the root, the answer is to upload it as a bundle in the UI and set the target to `bundle`, not to change the node. Hostname, expiry and signature findings are computed on the server from the chain as today. The node's own connection to the server is the one trust decision that cannot be central, because the node must trust the server before it can receive anything from it, the install script included: the node uses its host's operating system store for that, as `curl` does. A server on a private CA therefore needs that CA in the trust store of the node's host, which a network with its own PKI already has; the install script says so when the first download fails on the certificate.

**Scheduling is unchanged, the pool is not shared.** The scheduler's queue, jitter, interval and Check now work as for every target. When a due target is assigned to a node, the scheduler hands it to that node's queue instead of to a local worker; the node's lease count (its pool size) bounds how many run at once, and the local pool stays free for local probes. A Check all on a node with a hundred targets therefore drains through that node four at a time while the server's own targets are probed as usual. If the node has not polled within the offline window the dispatcher fails at once, so an offline node holds nothing. Nothing about leased jobs is persisted: after a server restart the queue is rebuilt from the database as it is now and due targets are dispatched again; a node that cannot deliver a result drops it, and the server asks again. Node targets keep the per-target jitter; there is no reason to batch a node's targets into one daily burst. Changing a target's "Probe from" is treated like changing its host: the legacy test is forgotten, the debounce streaks reset, and the target is checked soon, because a new vantage point is a new view of the service.

**Offline nodes do not look like unreachable hosts.** A target whose node is offline keeps its last state and shows "Waiting for node" with the time of its last check; its next check is held, no `unreachable` opens and no alert fires per target. Instead one `node_offline` finding opens on the node after 10 minutes, warning, escalating to critical when a target under it is overdue by more than its own interval. It is delivered on every enabled channel whose severity floor allows it and resolves with a recovery notice when the node polls again. When the node returns, its overdue targets are checked right away, spread over a few minutes. The offline clock starts fresh at server start: last seen is in the database, but after a server outage every node needs its reconnect backoff before it can be judged, so no node is offline during the first 165 seconds after start and no finding opens during the first 10 minutes.

**Installing a node is one command.** Nobody creates keys or edits files on the node. Settings › Nodes › Add node generates a one-time enrolment token, valid for one hour, and shows one command to run as root on the machine inside the network:

```
curl -fsSL https://tlswatch.example.nl/agent/v1/install/<token> | sudo sh
```

The server generates that script per token with its own URL and the token embedded, so the command is complete as shown. The screen also offers a Docker command (`docker run -d --restart unless-stopped -v tlswatch-node:/data ghcr.io/sjoerd305/tlswatch node -server … -token …`) and a manual variant (download the binary, run `tlswatch node enrol`, then `tlswatch node`) for hosts without systemd or without root. Add node is refused with a pointer to Settings › General while the public base URL is not set, because the script needs it. The screen also says which platforms the server can serve from its own binary and that any other needs the node host to reach GitHub, so an air-gapped network with a different architecture learns this before the script fails.

The script, which is embedded in the server binary and served without sign-in, does the following and nothing else, printing each step:

1. Checks that it runs as root, that `curl` or `wget` and `systemd` are present, and detects the operating system and architecture (Linux amd64, arm64 and armv7; an ARMv6 machine such as a first Raspberry Pi is refused by name, because the ARM build needs ARMv7).
2. Downloads the binary from `GET /agent/v1/download/<os>/<arch>` on the same server, with the SHA-256 the server sends alongside, and verifies it. The server serves its own executable when the platform matches its own, so a same-architecture network, including an air-gapped one, needs nothing from the internet; for another platform it redirects to the release asset of its own version on GitHub and sends that asset's checksum. Node and server are therefore always the same version at install time.
3. Creates a system user `tlswatch-node` with no shell and `/var/lib/tlswatch-node` (mode 0700, owned by it), installs the binary as `/var/lib/tlswatch-node/bin/tlswatch` owned by that user so it can update itself (see Updating nodes), links it from `/usr/local/bin/tlswatch`, and writes `/etc/tlswatch-node.env` with the server URL.
4. Runs `tlswatch node enrol`, which exchanges the token for the credential, writes it to `/var/lib/tlswatch-node/credential` (0600), and reports the system facts below. The token is now spent.
5. Installs and starts a systemd unit `tlswatch-node.service` (restart always, the system user, `ProtectSystem=strict` with the data directory as the only writable path, no new privileges) and prints "Connected to https://tlswatch.example.nl as <hostname>; finish in the UI".

Running the script again re-enrols the same machine with a new token. Removing a node from its machine is one command too: `sudo tlswatch node uninstall`, or, when the binary is gone or broken, `curl -fsSL https://tlswatch.example.nl/agent/v1/uninstall | sudo sh`, a second script served by the instance that needs no token. Both stop and disable the unit and remove the unit, the settings file, the link, the data directory with the credential and the system user, nothing else, and tell the admin to delete the node in the UI; the node's page shows both commands. The tests run both scripts with `sh` against a test server, with the system commands (`id`, `uname`, `systemctl`, `useradd`, `userdel`, `chown`) stubbed and every path under a temporary root (`TLSWATCH_INSTALL_ROOT`, which only the tests set), and check the checksum refusal, the files, their modes, the unit and the removal.

**The Add node screen watches the node arrive.** After showing the command the screen says "Waiting for the node to connect…" and polls the change stamp like the live pages. The moment the enrolment call lands, the screen swaps to the node's reported facts: hostname, operating system and version, kernel, architecture, container or not, tlswatch version, every non-loopback interface with its IPv4 and IPv6 addresses, the address the server sees the node from, whether it has an IPv6 route, and its clock offset from the server. The admin checks that this is the machine they ran the command on, enters a name (pre-filled with the hostname) and saves. Done. Until it is confirmed the node is *pending*: it polls and is shown, but no target can be assigned to it. A pending node that is not confirmed within an hour is deleted together with its credential, and "Reject" on the screen does the same at once. This confirmation is what makes a token in a URL acceptable: the token is one-time and expires in an hour, and should anyone else use it first, the admin sees the wrong hostname and addresses and rejects it, which revokes that credential.

**System facts** are reported at enrolment, at every start of the node and then once an hour (`POST /agent/v1/facts`): hostname, operating system name and version (from `/etc/os-release` or `uname`), kernel, architecture, container (yes/no), tlswatch version, interfaces with addresses, IPv6 route, the job kinds it runs, its limits (the allowlist as CIDRs, empty for any address, whether it allows local addresses, whether the allowlist came from the `-allow` flag or `TLSWATCH_NODE_ALLOW`, and the environment file when systemd started it with `/etc/tlswatch-node.env`), and the time, from which the server computes the clock offset. The server stores at most one report per node every five minutes; one sent sooner (a restart just after a report) is answered with 429 and a Retry-After, and the node sends it again then. The node page shows them with "reported 12 min ago". A changed hostname, address set, allowlist or local-address switch is recorded in the audit log with the old and new values, so a node that moved, was cloned or now probes more is visible; the first report of the limits, from a node just updated to a version that sends them, is not a change. Link-local addresses are left out of that comparison: they come and go with container interfaces and IPv6 privacy addresses and would fill the log. What a node reports is bounded before it is stored: 128 bytes per name, version or CIDR, 300 per error message, 64 interfaces with 64 addresses each, 256 allowlist entries, and a facts report at most once per five minutes per node, so a node cannot fill the database or the audit log. The facts are for identification and for support ("the node cannot reach 10.0.3.5 because it has no address in that subnet"); they are never sent anywhere else.

**Identity.** The credential is 32 random bytes that the server stores as a hash, as sessions are, and that the node keeps in its credential file next to nothing else; it is the node's only state. The credential is revoked by deleting the node, and disabling it stops all jobs. Rotate credential on the node page revokes the current credential at once (for a suspected leak) and shows a fresh install command; running it re-enrols the machine, which then waits for confirmation as a new node does, keeping its name and targets. Because the hash is in the database, a restored backup on the same URL keeps every node enrolled. Enrolment, confirmation, rejection, rotation, disabling and deletion are in the audit log.

**Node-side configuration** is deliberately small, as the UI-first rule asks: the node needs the server URL and the credential, and the server owns the name, the enabled state and which targets use the node. Only what the server must not be able to change stays on the node: an optional allowlist of CIDRs it may probe (an address outside it is refused like a local one), and whether loopback and link-local addresses are allowed there; such an address is probed only when both the node and Settings › General allow it. The node reports both with its system facts, and the node page shows them read-only under "Probe limits" with where to change them on that node: `/etc/tlswatch-node.env` and a restart of the service when systemd started it with that file, the `-allow` flag when that set the list, the container's environment for a container, the node's environment otherwise. A node from before the report shows "Not reported" until it is updated. The nodes list tags a node with an allowlist. Flags or environment, read from `/etc/tlswatch-node.env` by the unit: `-server` / `TLSWATCH_NODE_SERVER`, `-data` / `TLSWATCH_NODE_DATA` (the directory of the credential file, default `/var/lib/tlswatch-node`, `/data` in the image), `-workers` / `TLSWATCH_NODE_WORKERS` (default 4), `-allow` / `TLSWATCH_NODE_ALLOW` (CIDRs, empty means any), `-allow-local`, `-no-self-update` / `TLSWATCH_NODE_NO_UPDATE` (never replace the binary) and `-allow-unsigned-update` / `TLSWATCH_NODE_ALLOW_UNSIGNED_UPDATE` (also follow a development build of the server; see Updating nodes). An argument that is not a flag is refused, as is a variable that does not parse. `tlswatch node enrol -server -token` is the one-off exchange the script runs; `tlswatch node` with a token flag (or `TLSWATCH_NODE_TOKEN`) performs it itself at first start, retrying while the network comes up, for the Docker command. The image sets `TLSWATCH_CONTAINER=1`, from which the node knows it runs in a container (Docker's `/.dockerenv`, Podman's `/run/.containerenv` and Kubernetes count too) and keeps its credential in `/data`. The node honours `HTTPS_PROXY` and refuses a plain `http://` server unless `-insecure` is given, for a lab. It needs no volume beyond the credential file and runs in the same `scratch` image. It logs as the server does, JSON lines on stdout (the journal under systemd), one line per job with the target and the outcome, and never the credential. The operations guide gets a Nodes chapter: the one firewall rule, the proxy variables, the route alternative, and what to check when a node shows offline.

**Updating nodes.** Nodes update themselves from the server; nobody logs in to them. The rule is that a node converges on the server's binary: the download route serves what the server itself runs, so after a server upgrade every node follows, and after a server rollback they follow that too. Every poll carries the node's version. When it differs from the server's and the node is not in a container, the server sends an `update` job. The node finishes the probes it is running, takes no new ones, fetches the release's `SHA256SUMS` with its signature from `GET /agent/v1/release/sums` and checks the signature against the release key built into it, downloads the binary from `GET /agent/v1/download/<os>/<arch>`, verifies that its SHA-256 is the one the signed list names, writes it next to the running one, renames it into place keeping the old one as `tlswatch.prev`, writes a marker file with the old version, and starts the new binary in its own process (exec; should that fail it exits and systemd's `Restart=always` starts it), which polls and reports its new version. If the new binary has not completed a poll within five minutes of starting and the marker is present, it renames `tlswatch.prev` back and restarts; a node that comes back with its old version after an update is marked "update failed" on Settings › Nodes with the reason it reported (the old binary sends it in `X-Tlswatch-Update-Error` until a poll succeeds), or with "did not come back within five minutes" when it stays away, and is not updated again until an admin presses Update on it. The mark goes once the node reports a version other than the one the failed update started from: it was updated some other way, reinstalled or pulled. The marker is removed after the first successful poll.

- **One at a time.** The server updates one node at a time, waits for it to come back with the new version (five minutes at most; a node whose download or swap fails reports why on its next poll, so the wait ends at once with that reason), then takes the next, so a bad release never takes every network down at once. Settings › Nodes shows "updating 2 of 5" while this runs.
- **Automatic by default.** Settings › Nodes has one switch, "Keep nodes on the server's version", on by default; off, the page shows "update available" per node with Update and Update all buttons, and nothing happens on its own. Per node, Update is available whenever its version differs from the server's, whatever the switch. Every update is in the audit log with the versions.
- **Containers are pulled, not patched.** A node that reports container = yes is never sent an `update` job, because a replaced binary would be lost on the next container start and the image would stay old. Its row says "update by pulling the image", with the tag matching the server's version; the Docker command on the Add node screen pins that tag so the compose or Watchtower routine the customer already has does the rest.
- **The protocol outlives the binary.** `update` is part of protocol v1 from the first release, so any node ever shipped can be brought to the current version. The server keeps the previous protocol version working for one minor release alongside the current one. A poll on a protocol the server does not speak, older or newer (the server was rolled back), is answered with a fixed reply that every node version understands: the server's version and "update". The node then updates itself over the download route as above, in either direction, so no node ever needs a reinstall for a version mismatch. A node that does not replace its binary on that reply (a container, `-no-self-update`, a failed download) waits before it polls again, from one second doubling to a minute, so it never polls the server in a tight loop.
- **Only signed releases are taken.** Every release's `SHA256SUMS` is signed in the release workflow with an Ed25519 key (`scripts/releasesign`; the private half is a repository secret, the public half is in `internal/node/release.go`, so it ships in every binary). A node replaces its binary only with one whose checksum is in a list that key signed, whichever server handed it over: a server that is compromised, or a release edited on GitHub, cannot make a node run a binary of its own. The server fetches `SHA256SUMS` and `SHA256SUMS.sig` for its version once an hour, refuses to serve a download when the signature does not check, serves its own executable only when its bytes are the released ones and otherwise sends the node to the release asset (the Dockerfile and the release workflow build with the same flags, so an image of a tag normally holds the released bytes). A development build has no signature: a node follows one only when started with `-allow-unsigned-update`, and a node started with `-no-self-update` or `-insecure` never replaces its binary and reports why. Updates by hand, and the install script, verify the same checksum.
- **Only releases update automatically.** The comparison is on the version string, and automatic updates run only when the server's is a release tag (`vX.Y.Z` exactly). A development build (`2026.10.15-5efacf7`, `v0.2.0-5-g5efacf7`, anything `-dirty` or `dev`) never updates nodes on its own, so a half-finished build on a development server is not pushed into customer networks; Update on a node still works by hand and fetches whatever the server runs, which is only the server's own binary: it is offered for nodes on the server's platform, and such a node takes it only when it runs with `-allow-unsigned-update`. A node on another platform shows "no linux/arm64 binary for <version>" instead of Update, and is left out of Update all; the same holds on a release for a platform the release does not build.

The self-update is why the binary belongs to the node's user: a compromise of that user already runs arbitrary code as that user, so a writable binary adds no privilege, and `NoNewPrivileges` in the unit keeps it there. The signature is what keeps the server from being that compromise: without it, whoever controls the server would run code on every node, and the node-side allowlist would bound nothing. The install script therefore puts the binary under the node's data directory and links it from `/usr/local/bin` for people and for `uninstall`.

**Data model.**

- `nodes`: id, name, state (enrolling, pending, confirmed), credential hash, install token hash, sealed copy and expiry (while unspent; the copy, sealed under the secret key, lets the Add node screen show its command again after a reload, and is unreadable on another instance), created at and by, confirmed at and by, last seen, version, protocol version, address as seen by the server (following the proxy-trust rule, as sign-in addresses do), pool size, enabled, notes, and the system facts as reported (hostname, OS, kernel, architecture, container, interfaces and addresses, IPv6 route, job kinds, limits, clock offset) with the time they were reported, and the update state (requested, started, from and to, the last failure).
- `targets.node_id`, nullable: null means probed from the server. `observations.node_id`, nullable, so history stays right when a target moves between nodes.
- `findings.target_id` becomes nullable and `findings.node_id` is added, for `node_offline`; exactly one of the two is set, and each has its own unique index on open findings.
- Deleting a node is refused while targets are assigned to it; the confirmation page lists them and offers to move them to the server. Disabling is allowed at any time and holds its targets as when offline, without a finding.

**UI.** Settings › Nodes: a table with status dot, name, hostname, last seen, version (with "update available", "updating", "update failed" or "update by pulling the image"), address, IPv6 yes/no, number of targets, with pending nodes at the top; the "Keep nodes on the server's version" switch and Update all; Add node with the command screen and the arrival screen above; a node page with the system facts, the probe limits (read-only, with where to change them on the node), the targets assigned, the install command for re-enrolment and the uninstall command; per node edit (name, notes), rotate credential, disable, delete. The target form gains "Probe from" (This server, or a node by name) directly under the protocol. The targets list gains a node column and a filter chip per node; the target page shows the node in its configuration column and "Waiting for node" in place of the status while the node is offline. The overview shows a notice bar while a node is offline. Test without saving works through the node when one is selected, with the same timeout as a job. Findings and the overview list a `node_offline` finding under the node's name, linked to its page for admins. `/metrics` gains `tlswatch_nodes{state}` (online, offline), `tlswatch_node_last_seen_seconds{node}`, `tlswatch_node_jobs_total{node,result}` (completed, failed), and the scheduler's `tlswatch_scheduler_node_checks` and `tlswatch_scheduler_held`.

**Backup and restore.** The nodes table is in the backup with the credential hashes, so a restore keeps every node enrolled as long as the instance keeps its base URL; on a new URL the nodes must be re-enrolled with a fresh install command. During a restore the node dispatcher pauses with the scheduler: pending polls are answered empty, leased jobs are dropped and their results discarded, and the queues are rebuilt with the schedule afterwards.

**Security.** Only hostnames and certificate chains leave the customer network; the node performs one handshake and the STARTTLS preamble, reads no application data and returns nothing else. The node is told what to probe by the server, so a compromised server could aim it at internal addresses; the allowlist and the local-address rule on the node bound that, and every target assignment is in the audit log. A compromised server cannot go further than that, because the node replaces its binary only with a signed release (see Updating nodes). The reverse holds less: a confirmed node's results are taken as what it saw for its own targets, so a compromised node can misreport a handshake or put certificates into the inventory; what to trust is decided on the server, which verifies every chain itself against its own roots or the bundle and checks the hostname, so a node cannot mark a bad chain as trusted. It cannot reach other nodes' jobs, other targets, settings or users. The agent endpoints accept the bearer credential only, never a session cookie, and are rate limited. TLS to the server is required. The node credential is never logged and never shown back. The enrolment token travels in the install URL and lands in shell history and proxy logs; it is one-time, expires in an hour, and a node enrolled with it is useless until an admin confirms the reported hostname and addresses, so a stolen token yields a pending node that is rejected. The install and uninstall scripts are the only unauthenticated routes besides sign-in and `/healthz`; the binary download takes a node's credential or the unspent install token the install command carries, the install script is a fixed template with the URL and token filled in and is served only for an unspent token, and the uninstall script carries only the URL. Failed enrolments and rejected credentials count against the address like failed sign-ins: 20 in 15 minutes block it, but only requests without a valid credential or token, so nobody sharing an address with a node (a proxy, a NAT) can take the node offline by failing at it. The script is run as root by the customer, so it is short, does nothing outside the paths it names, and is readable before running (`curl … | less`).

**Not in this design**: several nodes per target (probing one host from inside and outside, which would make split-horizon differences an `inconsistent` finding), node-side scheduling or buffering during a server outage, and streaming from the node to the UI. The command envelope and the transport interface leave room for all three.

## Discovery

A target has to be known before it can be monitored, and the endpoints nobody listed are the ones that expire unnoticed. Discovery offers them from two places, a scan of the network and the names in Certificate Transparency, as a list to tick. Nothing it finds is monitored until an operator adds it, and what is added goes through Add many like any target.

**Network scan.** Under Targets › Discover, an operator or admin gives one or more ranges (CIDRs or single addresses, at most 4,096 addresses, a /20, per scan), the ports (default 443, 8443, 636, 993, 995, 465, 587, 5061; at most 16), the rate (default 50 connects per second, 1 to 200), and Probe from: this server or a node. The scan connects to every address and port at that rate, does the implicit-TLS handshake on each port and STARTTLS on 25 and 587, without SNI and without verifying, and records every endpoint that completed a handshake with its chain and the negotiated version. A connect or handshake gets three seconds. A scan from the server stores what it found and how far it got about once a second, so the scan page, which follows a running scan with the fast poll of the live pages, shows the progress move. On a node it is the `scan` job kind: the server splits the scan into chunks of about ten seconds of connects at the scan's rate (at most 256 addresses) and sends them one at a time, so the progress moves there too and a node that drops out loses one chunk; a chunk's timeout is its connects at the rate plus the connect timeout and 30 seconds. The node's allowlist and the local-address rule bound a scan as they bound a probe: an address outside the allowlist, or loopback and link-local unless Settings › General allows them, is refused without a connect and counted as such. The server takes a node's endpoints only for addresses and ports the chunk asked for.

*Limits*, so that a scan is discovery and not a scanner for hire: only operators and admins scan; a range must be private (10/8, 172.16/12, 192.168/16, the shared space 100.64/10, fc00::/7) unless Settings › General › "Allow discovery of public addresses" is on, which it is not by default; one scan runs at a time per node and one from the server; and every scan is in the audit log (`scan.start`) with its ranges, ports, rate and where it ran from. A scan from a node that does not list `scan` in its facts is refused before it starts, with the request to update the node, and the node is shown as unavailable in Probe from.

*Results.* The scan page shows the progress while it runs (it follows the scan like the other live pages) and then each endpoint found: address and port, protocol, subject, SANs, issuer, expiry, TLS version, and the target that already covers it, matched by address and port (a target whose host is the address, or whose last check reached that address). An endpoint with a target cannot be ticked. "Add selected" opens Add many pre-filled with one line per ticked endpoint and the scan's node as Probe from: the address and port, `protocol=smtp` for 25 and 587, and, when the first DNS name in the certificate (no wildcard) resolves to the address on the server, `sni=` with that name and the name as the target's name. A scan and its results are kept for 7 days; they are not inventory, and their certificates are not in Certificates. A scan the server was stopped during ends as failed with what it found so far.

**From Certificate Transparency.** The domain page gets "Names without a target": every name under the watch in a `known` or `acknowledged` issuance of the last 90 days that no enabled target covers by its host or server name, with the issuer and the date of the latest issuance naming it. A wildcard is listed when no target is on a name it covers, and cannot be ticked: it is not a host. "Add selected" opens Add many pre-filled with the ticked names. An `unexpected_certificate` finding offers "Add as target" next to Acknowledge, on the domain page and in the finding panel, which opens Add many with the issuance's names under the watch.

## Checks, findings and severity

Every observation runs the full set of checks (the test for legacy TLS versions once a day, see below); each failed check is a finding of one kind with one severity. Three severities: `info` (shown, never alerted by default), `warning`, `critical`.

| Kind | Opens when | Severity | Notes |
| --- | --- | --- | --- |
| `expiring` | The earliest NotAfter in the presented chain is within the warning or critical threshold: both its days and its share of the leaf's lifetime have passed (see Thresholds and defaults) | warning / critical | Counts whole days and the share left, the later of the two deciding; escalates from warning to critical as the date nears. The details name the share when it, and not the days, decided ("15 days left, 32 % of its lifetime") |
| `distrusted_ca` | The chain is anchored in a root that a root program distrusts, and the leaf falls under that distrust (see Distrust calendar) | warning / critical | A warning while the distrust is still ahead, critical from the day it takes effect. Only targets verified against the system store; a private PKI is in no root program |
| `revoked` | The leaf is listed in the CRL it names, or an address stapled an OCSP response saying it is revoked (see Revocation) | critical | The details give the date, the reason and where it was found: "revoked 2026-10-10 (key compromise), listed in the CRL at http://r11.c.lencr.org/7.crl". A fact about the leaf: it stays open while that leaf is served, also when its CRL later drops the entry, and resolves when a different leaf is served |
| `revocation_unknown` | The CRL of a served leaf could not be fetched or verified on 3 daily attempts in a row | info | Never alerted, whatever a channel's floor; shown on the target. A leaf without a CRL distribution point is normal and records nothing. Resolves on the next fetch that verifies |
| `must_staple` | The leaf carries the TLS feature extension with `status_request` (RFC 7633, OCSP must-staple) and the server sent no stapled OCSP response, or one a client refuses: not valid for the leaf, unknown to the responder, or past its next update | critical | Firefox refuses such a connection outright. Judged on every check. A server that fetches its staple lazily (nginx after a restart) sends none on the first handshake, so before reporting a missing staple the probe waits 2 seconds and asks once more, and takes the staple if the same leaf comes with one. A revoked staple is `revoked`'s business |
| `renewal_overdue` | A renewal-managed target still serves a leaf that has used more than its renewal point of its lifetime (default 75 %) | warning | The ACME client should have replaced it: "renewal was due 9 days ago; the certificate expires in 12 days". Escalation to critical stays with `expiring` |

The root a verified chain ends in is judged |

| `self_signed` | A self-signed leaf on a target whose trust mode is not `self-signed`, and that does not verify | critical | The fix is either the server, switching the target to `self-signed`, or adding the certificate itself to the target's CA bundle: a self-signed leaf in the bundle verifies and opens nothing |
| `hostname_mismatch` | The servername is not covered by the SANs | critical | Skipped when servername is empty (plain IP target). The CN is not used, as browsers no longer do: a certificate with only a CN is a mismatch |

| `default_certificate` | The certificate an address serves to a client that sends no server name (SNI) is expired, not yet valid, untrusted, self-signed or does not cover the server name | info | Never alerted, whatever a channel's floor; shown on the target. **Change detection.** A new leaf certificate is normal on an ACME-managed endpoint and suspicious on a manually managed one. A target carries the flag *renewal managed* (default on when the issuer is a known ACME CA such as Let's Encrypt, ZeroSSL or Google Trust Services, off otherwise; always editable).

- Renewal managed: a new certificate with the same issuer organisation, the same or a superset of SANs, and (when the target has a server name) still covering that name is recorded as `info` and not alerted. Any other change is a warning, so a renewal that drops a name is never taken for a routine one.
- Not renewal managed: any new leaf is a `warning` finding, so an operator confirms the replacement was intended. Acknowledging it resolves the finding.
- `self-signed` targets: pinned fingerprint; any change is a warning.

Changing a target's host, port, protocol or server name points it at another endpoint: the pin and the current certificate start over, so the next check sets a new baseline and opens no change. Changing only the trust mode starts a new pin.

**What changed.** The details of a change, the `certificate_changed` warning, its alert and the `info` renewal event under recent changes alike, carry a one-line diff of the old and the new leaf with the unchanged fields left out: the issuer (by its CN, with the organisation when that changed too), the intermediate when the issuer's name stayed but the certificate served after the leaf is another one, the subject, the SANs added and removed, the key type and size, the signature algorithm, the expiry date, and the lifetime in days when it changed. Example: "new leaf 3f2a91c0 from Let's Encrypt: SANs +api.example.nl −old.example.nl; key RSA 2048 → ECDSA P-256; expires 2026-11-30 → 2027-01-15; lifetime 90 → 47 days", or "renewed by Let's Encrypt: intermediate R11 replaced (5a1c0e2b → 9be7d3f4); expires …". The old leaf comes from the certificate store, its intermediate from the last observation that served it; when the old leaf has been pruned the details only say whether the SANs changed. A pinned self-signed certificate is compared with the pin.

A leaf that any address of the target served in the last 24 hours is not new: when the address serving the current certificate is briefly down and another address's certificate becomes current, and when it comes back, nothing opens.

A `certificate_changed` or `issuer_changed` warning (without an expected issuer) stays open until acknowledged or until an automatic renewal (the `info` case above) confirms the certificate is back on its normal cycle; that renewal resolves it without an acknowledgement. Any other new leaf leaves it open: a new `certificate_changed` warning replaces the old one's details, and an open `issuer_changed` stays as it is, so whoever acknowledges the new certificate still sees that the issuer moved.

**Legacy TLS versions.** The normal probe offers every version from TLS 1.0 to 1.3, so the server picks its highest and a server on TLS 1.3 says nothing about whether it would still accept TLS 1.0. To find out, each address that answered gets one more handshake per legacy version, TLS 1.0 and TLS 1.1, with the client pinned to exactly that version. The negotiated version settles some without a handshake: a server that negotiated TLS 1.0 accepts it and cannot accept 1.1. A completed handshake means accepted; a refused one (an alert or a closed connection) means refused; a connect failure, a STARTTLS failure or a timeout gives no verdict for that address.

SSL 3.0 is tested too, differently: Go has had no SSL 3.0 client since Go 1.14, so the probe sends a hand-built SSL 3.0 ClientHello (no extensions, the RSA, DHE and ECDHE suites of the era, export suites included) after the protocol's STARTTLS and judges the first reply, as sslscan and testssl.sh do. A ServerHello at version 3.0 means accepted; an alert, a closed connection or anything else means refused; a timeout gives no verdict. The handshake is never finished, so the verdict is "accepts", which for a version that must be off is the question. SSL 2.0 is not tested: OpenSSL removed it in 2016 and no current server stack contains it, so nothing can turn it back on, and anything old enough to still speak it also speaks SSL 3.0 and is caught there.

- The test runs on the first check of a target and then on the first check at least 23 hours after the last test that reached a verdict, so about once a day whatever the interval. Check now and Test without saving always run it. Changing the target's host, port, protocol or server name, or switching the test off and on, forgets the last test so the next check runs it. The cipher suite handshakes of the configuration grade below run in the same test, on the same schedule, under the same switch.
- Between tests `legacy_protocol` keeps its state; a test that finds all three versions refused on every answering address resolves it. A test where some address got no verdict and none accepted leaves the finding as it is and is repeated on the next check.
- TLS 1.2 next to 1.3 is normal and not reported. A server that offers TLS 1.0 only with cipher suites Go does not implement (DHE key exchange, for example) shows as refused.
- A node reports which versions and which suite classes its build tests with every checked result. A result from a node built before SSL 3.0, the raw suite classes and the DHE group were tested still counts what it accepted (an accepted TLS 1.0 opens the finding), but is not a full verdict: it resolves nothing and leaves the grade as it is until the node has updated, which it does by itself (see Updating nodes).
- Per target the test can be switched off ("Configuration test: Do not test" under Probe and reminder settings), for an appliance where the old versions and ciphers are known and cannot be changed. Switching it off resolves an open `legacy_protocol`, `weak_configuration`, `alternate_certificate` and `default_certificate` at the next check and leaves the target without a grade.
- The target page shows the result below the per-address table of the last check ("SSL 3.0, TLS 1.0 and 1.1 · refused · tested 3 h ago", or the versions accepted); the configuration column shows whether the test runs.

**Other certificates.** A server can hold more than one certificate for a name and choose by what the client offers, and the normal probe sees only the one it was given. The configuration test asks each answering address for the others, in the same daily test and under the same switch:

- *By key type.* A server with an RSA and an ECDSA certificate picks by the client's suites and signature algorithms, so a renewal job that replaced one and forgot the other leaves the clients that get the other with an expired certificate, unseen. One handshake pinned to TLS 1.2 offers only the suites of the key type the normal probe did not get (the ECDHE_RSA and RSA suites after an ECDSA leaf, the ECDHE_ECDSA suites otherwise). A completed handshake with a different leaf is the other certificate; a refused one means there is none. Every TLS 1.3 client supports both RSA and ECDSA (RFC 8446, 9.1), so the choice by key type is made at TLS 1.2, and a server that speaks only TLS 1.3 has no other certificate a client could get this way.
- *Without SNI.* One handshake sends no server name and records the certificate the server falls back to, often a forgotten default virtual host. It runs only when the server name is a DNS name, since an IP literal is never sent in SNI. A refused handshake (Cloudflare and others refuse a client without SNI) means none.
- Each other chain is verified against the target's trust mode and checked against the server name like the main one, on the server for a node target, and judged by the certificate checks. The alternate certificate is held to all of them, expiry thresholds included, and opens `alternate_certificate` at the worst severity it fails, alerted like any finding. The default certificate is held only to being valid (expired, not yet valid, untrusted, self-signed, not covering the name) and opens `default_certificate` as info, never alerted: few clients send no SNI today, and shared hosting serves another name's certificate as default as a matter of course, so it is worth seeing on the target, not worth a page. An other certificate that passes opens nothing.
- Between tests both findings keep their state, as `legacy_protocol` does: they are judged once a day, so an alternate certificate moves from warning to critical at the next test, not the hour it crosses the threshold. A test that found no problem on every answering address resolves them; one where an address got no verdict leaves them as they are. A node from before this test sends no verdict, so the findings wait for its update.
- The target page lists each other certificate under the address's grade ("RSA certificate too · 3fa2c1d0… www.example.nl · expires 2027-01-12 · valid", or what is wrong), with a link to it, and `tlswatch check` lists them per address under `other_certificates`. The other certificates are not added to the inventory or the target's history, which hold what the normal probe is served.

**TLS configuration grade.** The legacy test says whether old versions are still accepted; the grade says the same about the cipher suites and the key, and sums both up in one letter, A to F, per address and per target, so a list of a hundred targets can be sorted by how well they are configured. The grade is about the server's configuration only. Certificate validity (expiry, trust, hostname) has its own findings and does not enter the grade, so an expired certificate on a well-configured server is an A with a critical finding, not an F twice.

*What is tested.* The normal probe records the negotiated version and suite, which only shows the server's preference. In the daily test, after the legacy handshakes, each answering address is offered eight classes of suites at TLS 1.2, each on its own, so that an accepted handshake proves the class is accepted. The first four are suites Go's client does not implement, so they are offered in a hand-built ClientHello (the one the SSL 3.0 test uses, at TLS 1.2 with the server name, signature algorithm and group extensions) and judged on the ServerHello: the suite the server picks names the class. The four are offered together in one hello; while the server picks one, the hello is repeated without that class, so a clean server pays one hello and a bad one pays one per class it accepts. The other four get one Go handshake each, pinned to TLS 1.2 and offering only that class; a completed handshake names the suite.

| Class | Suites offered | Why it matters |
| --- | --- | --- |
| Export-grade | The `*_EXPORT_*` and `*_EXPORT1024_*` suites: 40-bit RC4, RC2 and DES40, 56-bit RC4 and DES | Keys that factor or brute-force in hours; FREAK forced clients down to them |
| NULL encryption | `TLS_RSA_WITH_NULL_*`, `TLS_ECDHE_*_WITH_NULL_SHA`, `TLS_ECDH_*_WITH_NULL_SHA` | Nothing is encrypted |
| Anonymous key exchange | The `TLS_DH_anon_*` and `TLS_ECDH_anon_*` suites | Nobody is authenticated: any machine in the path can be the server |
| DES | `TLS_RSA_WITH_DES_CBC_SHA`, `TLS_DHE_*_WITH_DES_CBC_SHA`, `TLS_DH_*_WITH_DES_CBC_SHA` | A 56-bit key |
| RC4 | `TLS_RSA_WITH_RC4_128_SHA`, `TLS_ECDHE_RSA_WITH_RC4_128_SHA`, `TLS_ECDHE_ECDSA_WITH_RC4_128_SHA` | Broken cipher, prohibited by RFC 7465 |
| 3DES | `TLS_RSA_WITH_3DES_EDE_CBC_SHA`, `TLS_ECDHE_RSA_WITH_3DES_EDE_CBC_SHA` | 64-bit blocks (Sweet32) |
| No forward secrecy | The `TLS_RSA_WITH_*` suites with AES: key exchange by RSA encryption | A leaked key decrypts recorded traffic |
| CBC with SHA-1 | The `TLS_ECDHE_*_WITH_AES_*_CBC_SHA` suites | Not AEAD; padding-oracle history. Common and not weak on its own, so it costs one step, not two |

*The Diffie-Hellman group.* Go has no DHE suites, so one more hand-built hello offers only DHE suites (RSA- and DSS-signed, AES, ChaCha20 and 3DES) and reads the size of the prime from the ServerKeyExchange that follows the ServerHello and the Certificate. The result is the group size in bits per address, 0 when the server accepts no DHE suite; a server that accepts the suite but closes before the key exchange counts as accepting it with the group unknown. A group under 2048 bits is a C and under 1024 an F (Logjam: a 1024-bit group is within reach of a state; 512-bit export groups were broken on commodity hardware), reported as "DHE with a 1024-bit group" in the grade reasons and in `weak_configuration`. 2048 bits and more is not a reason.

A refused handshake (an alert or a closed connection) means the class is not accepted; a connect failure, a STARTTLS failure or a timeout gives no verdict for that address and the test is repeated on the next check, as for the legacy versions. A server that negotiates only TLS 1.3 refuses every pinned 1.2 handshake and every raw hello and is graded on that. The suites a server accepts beyond the classes above are not a reason for a lower grade. Nine handshakes per address per day is the cost of the grade for a clean server (three versions, one raw hello, four Go classes, the DHE group), ten with the post-quantum one below, up to three more for a server accepting several raw classes, and two more for the other certificates above; a target with the test switched off pays none.

*The rules.* Each address starts at A and takes the lowest grade any rule gives it; the target's grade is the lowest of its addresses. Every rule that fires is a reason, and the reasons are stored and shown with the grade, so "B" is never shown without "accepts TLS_RSA_WITH_AES_128_GCM_SHA256 (no forward secrecy)" next to it. Two reasons are notes that lower nothing: "OCSP stapled" (see Revocation) and "post-quantum key exchange: yes" or "no" (below); a `grade_changed` event names only the reasons that lowered the grade.

| Grade | A rule that gives it |
| --- | --- |
| F | Accepts SSL 3.0 (POODLE). Accepts an export-grade, NULL, anonymous or DES suite. Accepts RC4. A DHE group under 1024 bits. An RSA or DSA key under 1024 bits anywhere in the chain. The highest version the server negotiates is TLS 1.0 or 1.1 |
| C | Accepts TLS 1.0 or 1.1 next to a newer version (the `legacy_protocol` case). Accepts 3DES. A DHE group under 2048 bits. An RSA key under 2048 bits or an EC key under 256 bits. A SHA-1 or MD5 signature in the chain (the `weak_signature` case) |
| B | Accepts a suite without forward secrecy. Accepts a CBC suite with SHA-1. The highest version is TLS 1.2 and no TLS 1.3 is offered |
| A | None of the above: TLS 1.2 or 1.3 only, every accepted suite forward secret, AES or ChaCha20 (CBC-SHA1 refused), keys of 2048 or 256 bits and more, SHA-2 signatures |

*Post-quantum key exchange.* Cloudflare reported on 29 September 2026 that about 70 % of browser traffic to its edge uses post-quantum key exchange, against about 15 % of origins; OpenSSL 3.5 and Go offer X25519MLKEM768 by default. Every handshake of the normal probe records the key exchange group it negotiated (shown after the cipher in the per-address table of the last check). In the daily test, each answering address gets one more handshake at TLS 1.3 offering X25519MLKEM768 and no other group, unless the normal probe already negotiated it: a completed handshake means the address negotiates post-quantum key exchange, a refused one that it does not, and no verdict (connect, STARTTLS, a timeout) leaves it untested. The result is a grade reason on each address, "post-quantum key exchange: yes" or "no", which does not change the letter under rule version 2; a later rule version may let it gate A, and that would be announced in the changelog. The target negotiates it when every answering address does, does not when one address does not, and is untested otherwise.

There is no A+ and no D: four grades are enough to sort a list and to argue with a vendor, and finer steps invite disputes about scoring instead of fixes. The rules are a table in the code with the version of the rules stored next to every grade (version 2 added the post-quantum note without changing a letter, version 3 the SSL 3.0 test, the export, NULL, anonymous and DES classes and the DHE group with their F and C; like any new version each makes every target take the test on its next check), so a later tightening (TLS 1.2 without 1.3 moving to C, say) re-grades on the next test and the history shows which rules a grade was given under.

*Findings.* One finding per cause, so that nothing is reported twice: `legacy_protocol` for the versions, `weak_signature` for the signature and the key size, and the new `weak_configuration` (warning) for the suite classes export-grade, NULL, anonymous, DES, RC4, 3DES and no forward secrecy, and for a DHE group under 2048 bits. CBC with SHA-1 and a missing TLS 1.3 lower the grade to B but open no finding: they are worth seeing in a list, not worth an alert. `weak_configuration` keeps its state between tests like `legacy_protocol`, resolves when a test finds every weak class refused on every answering address, and is left as it is by a test without a full verdict. A grade that changes between two tests is recorded as an `info` event (`grade_changed`, "grade B → C: accepts 3DES"), shown under recent changes on the overview and among the target's findings, without an alert of its own; the finding that caused a drop alerts. The drops of the week are listed in the digest.

*Where it shows.* The targets list gets a grade column (a letter badge, sortable; the first column to drop on narrow windows after TLS and last check) and a grade chip group in the filter bar. The target page shows the grade next to the countdown with its reasons as a list, per address when the addresses differ, and the configuration test result below the per-address table. Test without saving and `tlswatch check` report the grade and the reasons per address (`grade`, `grade_reasons`, and `weak_suites_accepted` next to `legacy_accepted`); `check` exits 1 for grade C and below unless `-no-config-test` is given, which also skips the legacy test (`-no-legacy` stays as an alias). The Prometheus endpoint exports `tlswatch_targets_by_grade` (enabled targets per grade) and `tlswatch_target_grade` per target with the grade as a label and its rank as the value (4 for A down to 1 for F). For post-quantum key exchange the targets list gets a PQ chip group (yes, no, untested) once a target has a verdict, the overview's Last 24 hours card a line "12 of 40 targets negotiate post-quantum key exchange" (of the enabled targets with a verdict), `/metrics` `tlswatch_targets_pq{state}` with state yes, no or untested, and `tlswatch check` `pq_kex` and `key_exchange_group` per address. The weekly digest lists targets whose grade dropped during the week. A node runs the same handshakes: the probe request carries the test flags, and the node reports what was accepted; the grade itself is computed on the server, so a rule change needs no node update.

**Distrust calendar.** Root programs remove CAs with a date and a scope: Entrust from November 2024, Chunghwa Telecom and NetLock after 31 July 2025, DigiCert's G1 roots in April and May 2026, and more every year. A certificate keeps working on the day of the announcement and fails months later in one browser, which no expiry check catches.

- *The table.* `internal/check` holds a table of distrust events, one per CA and root program (Chrome, Mozilla, Apple, Microsoft). An event names the roots it covers, an effective date, a rule, a short description and a link to the announcement. The rule is either *every certificate* (the root is removed, or no longer trusted for websites) or *issued after* a cutoff. Chrome judges the cutoff by the earliest SCT embedded in the leaf, falling back to NotBefore; the other programs judge NotBefore. The table ships in the binary, carries a version (`DistrustTable`), and gets new rows in an ordinary release. Nothing is fetched at run time, and since the server evaluates it at every check from the chain it stores, a new table applies to every target at its next check without a node update.
- *What it holds.* The first table, compiled on 18 October 2026 from the programs' own posts, Chrome's `root_store.textproto`, the Mozilla bugs and root lifecycle page, Apple's support article 121668 and Microsoft's Trusted Root Program notices, has the distrusts for cause (Entrust and its AffirmTrust roots, Chunghwa Telecom, NetLock, e-commerce monitoring's GLOBALTRUST 2020, and Apple's for Camerfirma and ComSign) and the root removals with a date: Chrome's and Mozilla's root-age removals of 2025 and 2026 (among them the DigiCert G1 roots), Mozilla's planned removal of roots with keys from 2008 and 2009 on 15 April 2027, and the removals that followed the distrusts. Chrome's rolling cutoffs on roots that are being replaced (USERTrust, GlobalSign R3, DigiCert G2 and others) are left out: certificates move to the new roots on their own, and their dates moved twice in 2026. Chrome publishes no release for a removal, so its date is the day the root left the Chrome Root Store source. The emergency removal of emSign ECC Root CA - G3, after eight of eMudhra's intermediates had their keys compromised, was added on 22 October 2026: Mozilla's row takes the day the root left NSS (20 October), Chrome's the release it announced (27 October).
- *Matching.* A root is matched by the SHA-256 of its public key, so a re-issued copy matches too, and by its key ID, so a chain whose server leaves the root out matches through the authority key ID of the certificate below it. Only the root the chain is anchored in counts: the one verification chose, or, when verification failed, the top of the chain as sent. An old root that a server sends a cross-sign from is no reason by itself. The table also carries the keys of the roots Chrome and Mozilla trust for websites today, and an event of either program does not apply when the chain also leads to one of those through a cross-sign: www.swisssign.com sends its 2022 root cross-signed by the removed Gold CA – G2, and both browsers anchor it in the 2022 root. Apple and Microsoft publish no such list, so their events judge the anchor alone.
- *The finding.* `distrusted_ca` opens when an event covers the anchor and the leaf falls under its rule. It is a warning until the effective date and critical from that day on; if the leaf expires before the effective date, nothing opens. The details name the root, each program and its rule: "chain roots in Entrust Root Certification Authority - G2; Chrome distrusts certificates from it issued after 11 Nov 2024; this one was issued 3 Dec 2024", or "Mozilla stops trusting it on 15 Apr 2027". It resolves when the chain no longer matches. Targets with trust mode `bundle` or `self-signed` are not checked.
- *Where it shows.* The chain view on the target page names the event next to the root it concerns, with a link to the announcement, and colours that link by the finding. The Certificates page marks the certificate "distrusted" and gets a Distrusted chip. The weekly digest lists the events that take effect in the next 90 days with the targets they will affect.

**Revocation.** Let's Encrypt removed OCSP URLs from its certificates in May 2025 and turned its responders off in August 2025, and the CA/Browser Forum made OCSP optional: a revocation check means fetching the CRL. OCSP is not queried.

- *The CRL.* For each served leaf with an `http://` or `https://` CRL distribution point (the first one; LDAP is not fetched), the CRL is fetched before the checks run, at most once a day per URL: a URL tried less than 23 hours ago is not tried again, whether that attempt worked or not, so targets sharing a CA's CRL fetch it once, and a revocation shows on the first check after the next daily fetch. `http://` is normal for CRLs; the signature is what counts. The CRL must be issued by the leaf's issuer from the served or verified chain and verify against its key. A partitioned CRL is followed through the distribution point of the leaf itself, and a CRL whose issuing distribution point names other URLs is refused, so another partition of the same CA, validly signed but without the leaf, is not taken for it. A delta CRL is refused, and so is a CRL issued before the copy held, so an old copy cannot be replayed. A CRL larger than 50 MB is refused and logged.
- *The cache.* The serials a CRL lists are stored per URL in the database with its this-update, next-update, size and the issuer key it was verified against; a fetch that brings the same issue again only marks the fetch. A failed fetch keeps the serials held, so a revocation already seen stays seen. A leaf is looked up by serial in the copy verified against its own issuer's key; a copy verified against another key says nothing of it. A URL that no served leaf has named for 7 days is pruned with its serials.
- *Where the fetch runs.* The server fetches, also for node targets, because a CRL URL is public by design. A node target verified against a CA bundle is a private CA whose CRL may be reachable only inside the network, so its CRL is fetched by the node with the `crl` job kind: the node fetches the URL under the same limits, its allowlist and its local-address rule, and returns the bytes, and the server verifies them as its own. A node that does not list `crl` in its facts gets no such job; the fetch fails with the request to update the node, and counts towards `revocation_unknown`. Loopback and link-local addresses are refused for a CRL as for a target unless Settings › General allows them.
- *Stapling.* The probe records the OCSP response a server staples (Go asks for one in every handshake), and the server judges it against the leaf's issuer from the chain: good, revoked, unknown (to the responder) or invalid (unreadable, or not signed for this leaf). A node sends the response as it got it, and the server judges it the same way. A stapled response saying revoked opens `revoked` too; its age does not matter to a revocation. A good staple is a grade reason, "OCSP stapled", that is shown but never lowers the grade; stapling is never required.
- *Must-staple.* A leaf with the TLS feature extension asking for `status_request` (RFC 7633) must come with a good staple, or Firefox refuses the connection. Such a leaf without one, or with one that is not valid for it, unknown to the responder or past its next update, opens `must_staple` (critical) on every check, after the probe has asked once more 2 seconds later for a server that staples lazily. Let's Encrypt stopped issuing must-staple certificates in 2025, but other CAs still do, and a server that loses its OCSP responder (a firewall change, the CA turning responders off) breaks for Firefox users the moment its last staple expires.
- *Where it shows.* The certificate panel on the target page has a Revocation row: "not revoked · CRL of 18 Oct, fetched 2 h ago" (with the node that fetched it, if one did, and the last failure, if the last fetch failed), "revoked 10 Oct · key compromise", "no CRL distribution point" or "CRL not fetched yet", the stapled status, and the CRL's URL.
- OCSP queries follow later, only for private CAs that still run responders, behind a per-bundle switch.

Fact findings (`expired`, `not_yet_valid`, `chain_untrusted`, `hostname_mismatch`, `weak_signature`, `legacy_protocol`, `weak_configuration`, `expiring`, `renewal_overdue`, `distrusted_ca`, `revoked`, `must_staple`, `alternate_certificate`, `default_certificate`) are raised on the first observation that shows them: there is no network noise in a certificate that is read successfully, nor in a handshake that completed. Only the network-shaped findings are debounced.

The negotiated TLS version and cipher suite, the key type and size, and the full chain are stored with every observation and shown in the UI; the daily configuration test adds what else the server would accept, and the grade sums it up.

## Certificate Transparency watching

Every publicly trusted certificate is published in Certificate Transparency logs before browsers accept it (RFC 6962; Chrome and Safari require it). That makes the logs the one place where a certificate for your domain shows up even when it was issued to the wrong person, by a CA you never used, or for a name you forgot existed. A target watches what a server serves; a domain watch watches what the world issues for a name, and tlswatch reports the difference: an issuance that no target serves.

**Domain watches.** A domain watch is a registrable name (`example.nl`) with "include subdomains" on by default, so one watch covers `portal.example.nl`, `*.example.nl` and everything below. Watches have tags, notes, channels and an enabled flag like targets, and are created, edited and deleted by operators under **Domains** in the navigation. There is no automatic creation from targets: an operator decides which domains are theirs, because a target on `portal.customer.example` does not make the customer's domain yours to watch.

**Source.** tlswatch does not tail the logs itself: the logs hold billions of entries and following them is a service, not a feature of a one-binary monitor. It asks an index of the logs for the issuances of one domain since the last poll. Two sources are supported, chosen once under Settings › Certificate Transparency: **Cert Spotter** (api.certspotter.com, the default; works without a key within its public rate limit, an optional API key raises it; the entries come with the certificate itself, so issuer and serial are read from it; an entry whose certificate does not parse is kept with the names, issuer and dates of the entry, so it does not stop the poll) and **crt.sh** (no key, no cursor, slower and rate limited by goodwill; the apex and `%.domain` are two queries, and the highest entry id seen is kept as the cursor). The source is a small interface (`Issuances(domain, cursor) ([]Issuance, cursor, error)`) with one implementation per service, so a third can be added, including a self-hosted index for an installation that must not talk to either. The settings page says in plain words what leaves the server: the watched domain names and nothing else, over HTTPS, to the chosen service. Polling goes from the server, never from a node, since the logs are public and the server already reaches the internet.

**Polling.** Every enabled watch is polled once an hour (interval configurable from 15 minutes to 24 hours, global; the housekeeping loop looks every minute for watches that are due), spread with jitter like checks, through the same outbound rules as the channels (a named connection, no credentials in the URL, the API key in a header). Adding a watch polls it at once, and Poll now on its page polls it by hand. A source answer is a list of issuances newer than the cursor, each with issuer, serial, names, validity and the log entry; the cursor is stored with the watch so a restart continues where it stopped. The first poll of a new watch takes the issuances of the last 90 days and records them without findings, so a new watch does not open one finding per existing certificate; an operator sees them on the domain page and can mark one unexpected by hand. Watches are polled one at a time, two seconds apart, and spread over the interval by a per-watch jitter, so a run over many watches never lands on the source as a burst. A poll that fails (crt.sh answers 502 when it is busy) is retried after 15 minutes, or after what a source answering 429 asked for; after 24 hours of failures `ct_source_failed` opens on the watch. A poll whose watch was deleted while the source answered records nothing, also when a new watch has taken the deleted one's ID meanwhile. A free source is shared with every other tlswatch installation, so the default interval is an hour, not a minute, and a watch that is disabled is not polled. Disabling a watch closes its open findings without notices; enabling it again opens the findings of its issuances that are still unexpected (and not expired), with their alerts.

**Matching.** Logs publish precertificates, which differ from the certificate the server will serve only by the poison and SCT extensions, so a fingerprint match is not possible; an issuance is matched to a served certificate by issuer CN and serial number, which are the same in both, and the match is stored. Matching happens at every poll, in the hourly sweep, and the moment a check stores a certificate the target did not serve before. An issuance is in one of four states:

| State | Meaning | How it gets there |
| --- | --- | --- |
| `known` | A target serves this certificate | Matched by issuer and serial to a certificate in the inventory, at the poll or when a later check lands; the first poll's backlog starts here too |
| `pending` | Probably a renewal on its way to a target | Every name in it is covered by an enabled target (a wildcard covers the names under it), and the issuer is the issuer that target serves today. Held for 48 hours, the time an ACME client needs at most to deploy what it just obtained |
| `unexpected` | No target serves it and nothing says one will | A name no target covers, an issuer no covered target serves, or a pending issuance still unserved after 48 hours. Opens `unexpected_certificate` (warning) on the watch with the names, the issuer, the date and a link to the log entry |
| `acknowledged` | An operator looked and it is fine | Acknowledging the finding, which resolves it; the issuance keeps the acknowledgement and the comment ("staging cert, Alex, 16 Oct") |

A `pending` issuance that a target serves within the hold becomes `known` and is recorded as an `info` event (`certificate_issued`) under recent changes, so an ordinary Let's Encrypt renewal shows up once, as a line, and never as an alert. An `unexpected` issuance that a target serves later resolves its finding with a recovery notice, as any finding does: the certificate turned out to be yours after all, deployed late. An issuance whose certificate has expired is closed silently, whatever its state. Names in an issuance that do not belong to the watched domain (a certificate for `example.nl` and `example.com` together) are shown but not judged.

**What it catches**, in the words of the alert: "a certificate for `admin.example.nl` was issued by Sectigo on 14 Oct and no target serves it", which is a forgotten host, a colleague's experiment, a hosting provider's automatic certificate, or an attacker with a validation foothold; and "a certificate for `portal.example.nl` was issued by Google Trust Services, while the target serves Let's Encrypt", which is a CA change nobody announced. Both are things an inventory of served certificates cannot see.

**CAA.** A CAA record (RFC 8659) names the CAs allowed to issue for a domain. An issuance by a CA the record does not allow is either a CA that ignored CAA, which is reportable to the root programs, or a record that changed after the issuance; both are worth seeing.

- *Lookup.* On every poll that answers, before the new issuances are recorded, the server looks up the CAA record set of the watched domain: the records of the name itself, else of its parent, and so on up to the top-level domain, as RFC 8659 prescribes. Go's resolver has no CAA queries, so tlswatch asks the name servers of the system (`/etc/resolv.conf`) directly, over UDP and over TCP when the answer is truncated; a name that does not exist or has no records is no record, any other failure (SERVFAIL, a timeout) is an error. The set is stored on the watch with the name it was found at and the time. A set that differs from the one stored is an `info` event, `caa_changed` ("CAA record changed: none (any CA may issue) → example.nl 0 issue "letsencrypt.org""), on the domain page and under recent changes; the first lookup of a watch sets the baseline without one. A failed lookup keeps the stored set and its error is shown on the domain page.
- *Judging an issuance.* Every new issuance of a poll (not a first poll's backlog, nor one already expired) is judged against the records as they are at that poll. Its issuer is mapped to the CAA identifiers its CA publishes by a table in the code (`letsencrypt.org`, `pki.goog`, `sectigo.com`, `digicert.com` and its brands, `globalsign.com`, `amazon.com` and so on), recognised by the issuer organisation or the start of the issuing CA's name and versioned like the grade rules (`caa.IssuerTable`, stored with each verdict). Each name of the issuance under the watched domain is judged by the records of that name if it has its own below the domain (at most 20 such lookups per issuance; the rest use the domain's set), else by the domain's set. A wildcard name is judged by `issuewild` when the set has one, else by `issue`; the issuer domain is the part of a value before its parameters, compared without regard to case; `issue ";"` allows no CA; a set without `issue` and `issuewild` allows every CA; an unknown property flagged critical allows none.
- *The finding.* An issuance a name's set does not permit opens **`caa_violation`** (warning) on the watch, one per issuance, next to any `unexpected_certificate` for it and independent of it: a certificate a target serves can still have been issued against the record. The details say who issued what and what the record allows: "Sectigo Limited issued for admin.example.nl, but the CAA record at example.nl allows only letsencrypt.org". It is acknowledged like `unexpected_certificate`, which resolves it and marks the issuance; it closes silently when the certificate expires, and disabling the watch closes it, enabling opens it again unless it was acknowledged. An issuer the table does not know is shown on the issuance as "CAA not evaluated", and an issuance of a poll whose lookup failed as "CAA lookup failed"; neither is a finding.
- *Where it shows.* The domain page has a CAA card with the record set, where it was inherited from and when it was looked up, or "No CAA record: any CA may issue" as a hint, not a finding. An issuance issued against the record carries an "against CAA" mark with the reason on hover. A watch with an open `caa_violation` shows as a warning ("CAA violation") in the Domains list.

**Where it shows.** The Domains page lists the watches with status, name, issuances in the last 30 days, open findings and last poll; the domain page lists the issuances newest first with state, names, issuer, validity and the matched target when there is one, filterable by state. Issuances are not inventory entries: the Certificates page stays the inventory of what is served, and an issuance appears there only once a target serves it. The overview counts open `unexpected_certificate` findings in its tiles like any warning, and the Findings page shows them with the domain in the target column. The weekly digest gets a section "Issued for your domains this week" with the known and the unexpected ones. Issuances follow the retention of observations, except that an issuance with an open finding is kept while the finding is open. Prometheus exports `tlswatch_ct_issuances_total` by state and `tlswatch_ct_last_poll_timestamp_seconds` per enabled watch. The navigation shows the number of watches next to Domains. Domain watches are in the backup and in the audit log like targets.

## Thresholds and defaults

Every threshold lives on the target, pre-filled from the global defaults an admin can change under Settings. Changing a default later does not touch targets that already have a value; a target field left empty follows the default.

| Setting | Default, manually managed | Default, renewal managed | Range |
| --- | --- | --- | --- |
| Warning, days before expiry | 30 | 10 | 1 to 365 |
| Warning, share of the lifetime left | 33 % | 20 % | 1 to 99 %, or days only |
| Critical, days before expiry | 7 | 3 | 1 to warning minus 1 |
| Critical, share of the lifetime left | 10 % | 7 % | 1 to 99 % and below the warning share, or days only |
| Renewal point (`renewal_overdue`) | — | 75 % | 50 to 95 %, per target only |
| Check interval | 24 h | 24 h | 1 h to 7 d |
| Addresses probed | all (max 8) | all (max 8) | all / first |
| Connect timeout | 10 s | 10 s | 2 to 60 s |
| Retries before `unreachable` | 2 | 2 | 0 to 5 |
| Debounce, consecutive checks | 2 | 2 | 1 to 5 |
| Configuration test (SSL 3.0, TLS 1.0/1.1 and cipher suites) | daily | daily | daily / off |
| Reminder interval, warning | 7 d | 7 d | 1 d to never |
| Reminder interval, critical | 1 d | 1 d | 1 h to never |
| Channels | all enabled | all enabled | subset |

The lower defaults for renewal-managed targets follow from ACME clients renewing at about two-thirds of the certificate lifetime: on a 90-day Let's Encrypt certificate a renewal normally lands with 30 days left, so a 30-day warning would fire on every healthy endpoint. With lifetimes shortening in the coming years these two defaults are the ones most likely to need tuning, which is why they are a global setting and not a constant.

**Thresholds as a share of the lifetime.** Under the CA/Browser Forum schedule, validity is capped at 200 days from 15 March 2026, 100 days from 15 March 2027 and 47 days from 15 March 2029, and Let's Encrypt already issues 6-day certificates. A fixed "30 / 7 days" stops meaning anything at those lifetimes: a 30-day warning on a 47-day certificate fires two weeks after issuance, and on a 6-day certificate on the day of issuance. So the warning and the critical threshold each take a number of days and a percentage of the leaf's lifetime remaining (`30 d and 33 %`), and a threshold fires once both have passed: the later of the two wins. The days are lead time, how long a person needs to act, which does not shrink with the lifetime; the share says whether the certificate is on its normal cycle. So a long-lived certificate keeps its day thresholds (a 1-year manually managed certificate warns at 30 days, as before), a 47-day one warns at about 15 days, and a 6-day Let's Encrypt certificate on the renewal-managed defaults warns at about 29 hours and turns critical at about 10, instead of warning from the day it is issued. The lifetime is NotAfter minus NotBefore of the leaf; the time remaining runs to the earliest NotAfter in the chain, as for the days. In Settings › Defaults an empty percentage means days only. On a target an empty field follows the default, as every target field does, and 0 means days only. Targets saved before the percentages existed keep their stored day values and take the percentages from the defaults. A late renewal of a long-lived renewal-managed certificate is caught by `renewal_overdue` well before either threshold.

**Renewal point.** A renewal-managed target opens `renewal_overdue` once its leaf has used more than the renewal point of its lifetime: 75 % by default, which gives margin past the two-thirds where ACME clients renew. It is set per target, from 50 to 95 %, under "Probe and reminder settings". The outage of the coming years is a renewal that ran and was never deployed, or an ACME client that silently stopped, and this is the finding that catches it while there is still time.

A threshold's days have passed when strictly fewer than N whole days remain, so "warning 30" alerts on the first check that sees 29 days or less (once the share has passed too), and its share when strictly less than it remains. The time left shown in the UI and in alerts uses the same truncation, in hours below 7 days ("expires in 31 h"). Thresholds still count in whole days or a percentage, never in hours.

**Interval guard.** A target whose check interval is longer than a fifth of its leaf's lifetime gets a note on its page ("Checked every 1 d; this certificate lives 6 days"). The note opens no finding.

## Alerting

Alerts fire on state transitions, not on every check, so a daily check never produces a daily e-mail for the same problem. Specified behaviour:

1. **Open**: one alert when a finding opens, to every channel attached to the target whose minimum severity is met.
2. **Escalate**: one alert when a finding's severity rises (warning to critical).
3. **Remind**: a repeat at the target's reminder interval while the finding stays open, with the same message plus "still open since". Acknowledged findings are not reminded.
4. **Recover**: one notice when the finding resolves, so the receiver knows it is done. Recovery is sent to every channel that was told about the finding: the open alert, an escalation or a reminder, so a channel added while the finding was open hears that it is done. The alert log of a finding that is still open is kept past the history retention for this.
5. **Acknowledge**: an operator acknowledges a finding in the UI, optionally until a date (snooze). Acknowledging suppresses reminders, never the escalation or recovery notice. An acknowledgement on `certificate_changed` resolves it; on other kinds it expires when the finding resolves, when it escalates (an acknowledged warning that turns critical is reminded again) or when the date passes.
6. **Digest**: an optional weekly e-mail (day and hour configurable; a digest whose hour passed while the server was down goes out at the first chance within a day, after that the week is skipped) listing open findings, certificates expiring in the next 30 days, targets that failed their last check, targets whose grade dropped, the certificates issued for watched domains that week, and the distrust events taking effect in the next 90 days with the targets they will affect. Off by default. `info` findings (expected ACME renewals) are recorded as already resolved and are not in it: they show under recent changes on the overview and nowhere else.

**Channels** are configured globally by an admin; each target selects which of them apply (default: all). A channel has a minimum severity: a Telegram chat can take only `critical` while the mailbox takes everything.

Every HTTP transport treats a 429, or a 503 with Retry-After, as a request to wait: the retry is postponed by at least the time asked. A server error (5xx), a timeout (408) or a conflict (409) is retried with the normal backoff. Any other client error (4xx: a webhook deleted, a token revoked, a message refused) cannot be changed by a retry: the alert is marked failed at once with the service's answer, which Settings › Channels shows. A Telegram chat that does not exist or blocked the bot is settled the same way, so a retry for another chat skips it. Errors never contain the credential, also when the URL itself is the credential: connection errors are reported without the URL, and the URL and its path are redacted from any other text. URLs must be `http://` or `https://` without embedded credentials; an admin chooses them, and there is no other restriction on the host, since self-hosted services on private names are the common case.

One message per finding; a run that opens many findings at once (a new bundle of targets, an outage) is collapsed into one message per channel listing them, capped at 50 lines. The weekly digest is always a message of its own, never a line in such a batch, and a PagerDuty channel takes every alert on its own: the outbox hands a lone alert's event (open, escalate, remind, recover) and finding to the transport, which a batch has none of.

**Calendar feed.** Under Account, any user creates a secret calendar URL, `/calendar/<token>.ics`, for all targets or for the targets with one tag, and subscribes to it in a calendar. It lists one all-day event per certificate an enabled target serves, on its expiry date in the server's time zone ("Certificate expires: portal.example.nl (Portal)", with the issuer, the targets and the fingerprint in the description and a link to the target when one serves it), and for renewal-managed targets one more on the renewal point ("Renewal due: …", the earliest of the targets sharing the certificate). The UID is the certificate's fingerprint (`<fp>@tlswatch`, and `renew-<fp>@tlswatch`), so a renewal moves the event instead of adding one. The feed is read-only; every role sees every target, so it shows what its owner could see in the UI. The token is 32 random bytes, shown once when the feed is created and stored as a SHA-256 hash, like a session; the feed answers only while its user is enabled, and Revoke on the Account page ends it. Creating and revoking are in the audit log (`calendar.create`, `calendar.revoke`) with the scope. The list shows each feed's scope, creation and last fetch (written at most hourly). The route is public, the token in it being the credential, since a calendar client cannot sign in; an unknown token is a 404.

**Message content**: target name and `host:port`, finding kind and severity, days left (hours below 7 days) and the expiry date, issuer and subject CN, fingerprint (short), the address that failed, and a link to the target in the UI. A finding on a domain watch names the domain, the issued names, the issuer, the issue date and the log entry instead, with a link to the domain page. Mail is `multipart/alternative`: a plain-text part and an HTML part styled like the UI (the dark top bar with the shield mark and the wordmark, a white card, a status pill, a large countdown for expiry, uppercase labels with mono identifiers, an "Open in tlswatch" button; dark tokens for clients that support `prefers-color-scheme`; inline styles, system fonts). The shield mark of the UI and favicon is a PNG carried in the mail itself (`multipart/related`, referenced by Content-ID), because most mail clients do not show inline SVG and many block remote images. Batches, the weekly digest (stat tiles and three lists) and the channel test message use the same layout. Telegram, Slack and Discord messages are plain text with the same fields on separate lines, the subject first; ntfy gets the subject as the title and the fields as the message; a webhook gets the subject and the plain text in its JSON document. The subject line starts with the severity in brackets so mail rules can route it: `[critical] portal.example.nl:443 expires in 6 days`.

**Delivery** is queued in SQLite and retried with backoff (1 min, 5 min, 30 min, then hourly for 24 hours), or later when the transport asks for it (a Telegram rate limit, a 429 from a webhook); after 24 hours the alert is marked failed and logged as given up. A channel that is down does not block another. Every attempt at the same alerts carries the same reference (the webhook's `ref` and `X-TLSWatch-Ref`, the mail's Message-ID), so a receiver that got a message whose answer was lost can recognise the retry. A Telegram channel with several chats tries every chat; a retry goes only to the chats that did not get the message yet. An SMTP channel with several recipients works the same way: the relay judges each recipient, the mail goes to the ones it accepts, and a retry goes only to those it refused with a temporary (4xx) reply. A permanent (5xx) reply, for one recipient or for the whole message (sender refused, authentication failed, content rejected), is not retried: the alert is marked failed at once with the relay's answer, which Settings › Channels shows. When some recipients are refused for good while others are retried, the alert that the retry then delivers keeps naming the refused ones ("not delivered to …"), and the channel's last delivery shows "partly". A test button per channel sends a sample message. Every delivery and its result is kept in the alert log for 180 days.

## Inventory and user interface

The UI is an operations console: the home screen answers "what needs attention now" before anything else, lists are dense and sorted by expiry, and colour means status only. All text in English. Navigation: **Overview**, **Targets**, **Domains**, **Certificates**, **Findings**, **Settings** (admin only), with live counts, plus the account menu. The design canvas in `design/` is the reference for every screen below.

**Grouping** is by free-form tags (`customer:contoso`, `site:amsterdam`, `sip`), shown as badges, filterable, and usable as a column to group the targets list. Tags are enough for 10 to 100 targets and scale by convention; a fixed group hierarchy is deliberately left out. Every target has a notes field for owner, ticket number or renewal procedure.

**Target pagination.** The targets page shows at most 100 matching targets per page. Filters, sort order and chip counts cover the whole inventory; changing a filter or sort returns to the first page. Tag grouping groups only the current page, and bulk selection acts on its distinct targets. Search is a literal Unicode-case-insensitive substring, including `%` and `_`. With JavaScript, typing waits 350 ms before fetching the matching page and preserves focus; without it, the Filter button submits the same search. Live updates refresh the current bounded page.

**Filter chips** combine across groups: one active chip per group, and a row shows when it matches all of them and the filter text. A chip's count is the number of rows it would show given the filter text and the other groups' active chips, its own group left out, so the counts follow every filter as it changes, live with JavaScript and on the server-rendered page without it. A chip that would show nothing stays in place, dimmed with a count of 0, so a combination like grade F and tag mail is visibly empty before it is chosen. The "Any tag" and "Any issuer" chips carry no count.

**Interaction.** A row in a list is clickable as a whole and follows its primary link (the target, the finding, the certificate, the user or channel to edit). "/" focuses the page's filter field. Past expiry is shown as "expired", not as negative days. Deleting a target, channel, bundle or user asks for confirmation; disabling does not, because it is reversible. A form disables its buttons while it is being sent, so a slow action (a channel test, a save) is not sent twice.

**Export and import.** Targets and domain watches export as one YAML document (Settings › Export, and `GET /api/v2/export` for a token of any role): `version: 1`, then `targets` ordered by endpoint and `domains` by name, each with only the settings that differ from what a new one starts with in the Add target and Add domain forms. A target is its `host`, and where they differ from the defaults `port` (the protocol's), `protocol` (tls), `server_name` (the host, for a DNS host), `name` (the host), `node`, `trust` (system), `bundle`, `renewal` (auto), `expected_issuer`, the threshold, interval, probe and reminder overrides (`warn_days`, `crit_days`, `warn_pct`, `crit_pct`, `renewal_pct`, `interval_s`, `timeout_s`, `retries`, `debounce`, `remind_warn_s`, `remind_crit_s`; left out, Settings › Defaults applies), `first_address_only`, `skip_config_test`, `channels` (left out, every channel; `[]`, none), `tags`, `notes` and `disabled`; the names match the demo file's. A domain watch is its `name`, with `subdomains: false`, `channels`, `tags`, `notes` and `disabled` when they differ. Channels, CA bundles and nodes are named, never copied, and the document holds no credentials, history or state. Pasted or uploaded under Targets › Add many, the same document is imported: unknown fields, a version other than 1, a second document, an unknown channel, bundle or node name, an invalid value or a repeated target is reported, every problem at once with its place (`targets[3] mail.example.nl: Port must be 1 to 65535`), and nothing is planned. Targets are matched by host, port, protocol and server name (a DNS host stored without a server name matches its export, which leaves the server name out); domain watches by name. The import preview shows the plan; importing re-reads the file, and when the plan differs from the preview (something changed meanwhile) shows the new preview instead. A changed target or watch takes exactly the file's configuration, the fields left out returning to their defaults, and keeps its history; enabling or disabling one goes through the same path as the Enable and Disable buttons. Nothing is deleted unless the removal box is ticked. The whole import is one transaction, all or nothing; each change is audited (`target.create`, `target.update`, `target.delete`, `domain.…`, with `import=true` and the changed fields), added and changed targets are checked soon, and new watches polled. Importing an unchanged export changes nothing, so the document can be kept in a repository as configuration.

**Live pages.** Overview, Targets, a target's page, Certificates and Findings keep themselves current. They poll a small change stamp (`/api/v1/stamp`): every 4 seconds while checks are queued or running, a target has never been checked, or a node is enrolling or waiting for confirmation (so the Add node screen shows the machine within seconds of its enrolment), otherwise every minute, and not at all while the browser tab is hidden. When the stamp changes, a fresh render of the same URL is swapped in. The filter, the expanded certificate and the selected finding are part of the URL and survive. A refresh is skipped while the user is typing, has text selected, has unsaved input or ticked checkboxes, or has a menu open. These background requests do not count as activity for the session idle timeout.

The healthy state is the common one and must read as good news: "14 targets, nothing due within 30 days, last run 04:17". Empty states say what to do next ("No targets yet — add one or run `tlswatch check host`"). Below 760 px tables fall back to cards: the main lists (targets, expiring next, certificates, findings) to compact ones of a few cells (status, name, host, days left), the settings tables to one labelled line per column. The reminder to set the public URL is shown on the overview only. Status colours are used identically everywhere: green healthy, amber warning, red critical and expired, grey disabled or unreachable, blue only for informational changes.

| Users and roles: add or invite, edit, set a password (without SMTP), unlock, disable, delete | | | yes |
| Audit log | | | yes |

**Local login**: e-mail and password. An admin creates the account. When an enabled SMTP channel exists, the user receives a one-time link (7 days valid) by e-mail and chooses their own password; the link is also shown to the admin in case the mail does not arrive. Without an SMTP channel, the admin sets the first password in the form (or creates a one-time link to pass on), and can later set a new one for a local user; that also ends the user's sessions and clears a lockout. With SMTP, admins cannot set passwords: they send a new link instead. Users change their own password under Account. Every password is at least 12 characters, checked against a local list of leaked passwords. Password hashes use Argon2id. Five failed attempts block the account for 15 minutes, except from the address it last signed in from, so failures from elsewhere cannot keep its owner out (the per-address limit of 20 failures in 15 minutes still applies there, and from 25 failures in a row the lock holds for that address too); the count is kept in the database in one statement, so attempts in parallel all count; the error message does not reveal whether the e-mail exists, and an address without an account locks the same way. Admins see a locked account in the user list and can unlock it; setting a new password through a one-time link also clears the lock.

**Two-factor sign-in (TOTP)**: a local account can add a code from an authenticator app (RFC 6238: HMAC-SHA-1, 6 digits, 30-second steps, one step of drift either way). It is set up under Account: a QR code of the `otpauth://` URI, drawn on the server as an inline SVG by tlswatch's own encoder (byte mode, level M, no library), the key as text beside it, and a code from the app to confirm; until confirmed nothing is stored, the secret travelling sealed in the form for 15 minutes. A wrong code at setup keeps the same QR code. Confirming shows 10 single-use recovery codes once (12 characters, about 59 bits, stored as SHA-256 hashes) and signs the user's other sessions out. The secret is sealed under the secret key, bound to the user's row, like the channel credentials. Sign-in then takes the password, then the code on a second screen; between the two the browser holds only a sealed, HttpOnly state that lasts 5 minutes, and no session. A code is accepted once: the last accepted step is stored and an older or equal step is refused. A recovery code works in the same field, typed with or without dashes, and is spent; its use is audited and the user is told how many are left. A wrong code counts towards the lockout exactly like a wrong password, and the right password does not reset the count while the code is missing, so the password buys no fresh guesses at the code. Under Account a user makes new recovery codes or turns TOTP off, both with a current code. An admin can require TOTP per role (Settings › Sign-in, viewers, operators and admins each): a local account of such a role without TOTP is sent to the setup page by every page until it is set up, the JSON API refuses it, and it cannot turn TOTP off. An admin resets a user's TOTP under Users (not their own), which removes the secret and recovery codes, ends their sessions and is audited. Single sign-on accounts have no TOTP here; their provider does that.

**Single sign-on**: OpenID Connect with Authorization Code, PKCE (S256), state and nonce, implemented against the standard library plus `golang.org/x/oauth2`, for two providers side by side: Google, and one generic provider. Google is the generic implementation with its endpoints and issuer preset, plus the Workspace domain (`hd`) and a verified e-mail address required. The generic provider covers Microsoft Entra ID, Keycloak, Authentik, Okta and the like: an admin gives the issuer URL (HTTPS), and the authorisation, token and userinfo endpoints are read from its `.well-known/openid-configuration`, kept for an hour; the document must name that issuer (a trailing slash aside) and HTTPS endpoints. Also a client ID and secret (sealed), the scopes (default `openid email profile`, `openid` always included), an optional allowed e-mail domain, and an optional role claim. The ID token comes straight from the token endpoint over verified TLS, so per OpenID Connect Core 3.1.3.7 its issuer, audience (and authorised party when several), expiry and nonce are checked instead of its signature. An e-mail address the token states unverified is refused; one without the claim is accepted (Entra ID sends none), which is why the issuer must be the organisation's own, a single tenant. When the ID token lacks the e-mail address or the role claim, they are read from the userinfo endpoint, whose subject must be the token's. Sign-in is only possible for an e-mail address an admin has already added with that provider's login method (allowlist); there is no self-registration. With a role claim (a top-level claim such as `groups` or `roles`, or a path such as `realm_access.roles`; a string or a list), admins name the groups for admin, operator and viewer; the highest role whose group the user is in decides the role at every sign-in, the change audited, and a user in none of them cannot sign in. The last enabled admin keeps the role whatever the claim says. "Create users from the role claim" (which needs the claim) creates a user who is not there yet with that role, audited as the sign-in's. The login method is per user: a single sign-on user has no password or TOTP. Switching a user to another method ends their sessions, and switching to single sign-on also removes the password, TOTP and recovery codes and voids any password link still out. The two providers have their own callbacks (`/auth/google/callback`, `/auth/oidc/callback`), and the sealed state names its provider, so one provider's state does not complete the other's sign-in.

**Removing users.** Disabling a user ends their sessions and keeps the account for later; deleting removes the account with its sessions and one-time links for good. The audit log keeps their entries, which record the e-mail address. Nobody can delete their own account, and the last enabled admin can be neither deleted, disabled nor demoted.

**API tokens** authenticate the REST API (see REST API). Under Account a user makes a token with a name, a role no higher than their own, and an expiry of 30, 90 or 180 days or a year; only admins may choose no expiry. The token (`tlsw_` and 43 random characters, 256 bits) is shown once and stored as a SHA-256 hash like a session's; the list shows its first characters, role, expiry, and last use with the address, written at most once a minute. At most 50 per user. A token acts with the lower of its role and its user's current role, so demoting a user demotes their tokens at once; disabling or deleting the user deletes them (enabling again does not bring them back), and an expired one opens nothing. Making and revoking a token are audited (`token.create`, `token.revoke`). A token never works for the browser UI, and a session cookie never works for the API, so CSRF does not apply to it.

**Sessions**: server-side session store in SQLite, cookie `HttpOnly; Secure; SameSite=Lax`, named with the `__Host-` prefix over HTTPS (as is the pre-sign-in CSRF cookie) so a cookie planted from a sibling subdomain or over plain HTTP is never read, and every non-GET request a browser marks `Sec-Fetch-Site: cross-site` is refused before anything is read, 8 hours idle timeout (the live-page polling does not count as activity, so an open tab does not keep a session alive) and a 7-day maximum age after sign-in, CSRF token on every state-changing form and JSON call. While no account exists, every page redirects to a setup screen where the first admin is created with their own e-mail address and password and signed in directly; the screen disappears once an account exists. The setup screen also restores a backup (see Backup and restore), so a new installation takes over from an old one without a throwaway admin; that too is refused once an account exists, checked on the writer connection in the same step as the restore. The check and the insert are one transaction, so concurrent attempts create one admin only. Scripted installs can use the `create-admin` subcommand, which prints a one-time password link on the terminal (stderr) or writes it to a file (`-out`, mode 0600), so it does not land in a captured stdout.

**Authorisation** is one decision function role × action, called by every handler and covered by a negative test suite (every role tried against every action it must not have).

**Demo mode** (`TLSWATCH_DEMO`, the path of a demo file) runs a public demo without accounts. Nobody signs in: every visitor is the built-in demo role, which views targets, domains, certificates, findings and history and does nothing else (not even what a viewer does under Account). The role is never stored on a user and cannot be assigned. Session cookies are not read. The sign-in, sign-in code, setup, invitation, single sign-on, account and settings pages redirect to the overview, so a new demo instance without accounts never offers its setup screen. Every write is refused with "This is a demo: it shows the data, and nothing can be changed.", except the theme switch, which a demo visitor keeps in the theme cookie alone. Every page shows a strip saying it is a read-only demo, with a link to the project. The user menu holds only the theme. A demo is public, so its `/robots.txt` disallows all crawling; a real instance has no `robots.txt`, since a crawler only reaches its sign-in page and must be let in to read the noindex there (see Security, Headers).

Demo mode refuses to start on a database that has user accounts: that is a real instance, and demo mode would show its data to anyone. On start, it reads the demo file: JSON with `bundles` (name, PEM), `targets` (`host`, and optionally `port`, `name`, `protocol`, `server_name`, `trust` (system, bundle or self-signed), `bundle`, `renewal` (auto, managed or manual), `expected_issuer`, `warn_days`, `crit_days`, `first_address_only`, `skip_config_test`, `disabled`, `tags`, `notes`) and `domains` (`name`, `subdomains`, `tags`, `notes`). Left-out fields follow the Add targets form. An unknown field, an unreadable file or a file without targets and domains stops the start. The file fills an instance that has no targets, domain watches or CA bundles yet, in one go, all targets or none, audited as `demo.load`; an instance that has any is left as it is, so a restart keeps the history. Checks, CT polls and the configuration test then run as usual. A demo has no channels, so it sends nothing. The demo file lives outside the binary; the repository's is `demo/demo.json`, with `demo/compose.yaml` to run it.

## REST API

The public API lives under `/api/v2`; the internal `/api/v1` stays private to the TypeScript. It takes `Authorization: Bearer <API token>` and nothing else: it never reads the session cookie. `GET /api/v2/openapi.json` (OpenAPI 3.1) is served without a token; it is generated from the same table of endpoints that registers the handlers and from the Go types of their bodies and responses, so it cannot drift from them, and names each endpoint's role action as `x-role-action`.

Target list pagination runs in SQLite, ordered by ID with one extra row to determine `next_cursor`. Only that page's certificate summaries and channel links are loaded. Existing zero-padded ID cursors remain valid. Invalid limits and cursors are rejected before database access. Full exports still read the entire inventory; certificate and channel lookups use batches of at most 500 parameters.

| Endpoint | Role | What it does |
| --- | --- | --- |
| `GET /targets` | viewer+ | List, with the filters of the targets page: `status`, `tag`, `q`, `node` (`server` or an id), `grade` (or `none`), `pq` |
| `POST /targets` | operator+ | Add: `host` required, everything else as the Add target form starts; the first check is queued. 201 with `Location` |
| `GET /targets/{id}` | viewer+ | One target: configuration (overrides as null when they follow the defaults, and `effective` with the values in force) and state |
| `PATCH /targets/{id}` | operator+ | Change: the fields sent change, the rest stay; `null` returns an override to its default; a new host carries a server name that followed the old host along; `enabled` enables or disables as the buttons do |
| `DELETE /targets/{id}` | operator+ | Delete with history. 204 |
| `POST /targets/{id}/check` | operator+ | Check now; the new state |
| `GET /certificates`, `GET /certificates/{fp}` | viewer+ | The inventory, with the page's filters (`window`, `issuer`, `key`, `q`, `all=1`) and where each is served; one by SHA-256 fingerprint with its PEM |
| `GET /findings`, `GET /findings/{id}` | viewer+ | `state` open (default) or resolved (within the retention), `severity`, `kind`, `target_id`, `domain_id` |
| `POST /findings/{id}/ack` | operator+ | Acknowledge: `until` (a date, through its end in the instance's time zone, or an RFC 3339 time) and `comment`; as in the UI, a change finding is confirmed and resolved. 409 when it is no longer open |
| `GET /domains`, `POST /domains`, `GET`, `PATCH`, `DELETE /domains/{id}` | viewer+ to read, operator+ to write | Domain watches, as targets; a new watch's first poll runs in the background |
| `POST /domains/{id}/poll` | operator+ | Poll now; the new state, or 502 `poll_failed` |
| `GET /issuances` | viewer+ | `domain_id`, `state` |
| `GET /channels` | admin | Channels without credentials: kind, floor, destination, last delivery |
| `POST /channels/{id}/test` | admin | Send the test message; 502 `delivery_failed` with the reason |
| `GET /export` | viewer+ | The export document (see Export and import), as `application/yaml` |

Bodies are JSON objects; an unknown field, a value of the wrong type or another content type is refused. Times are RFC 3339 in UTC, or null. Lists answer `{"data": [...], "next_cursor": ...}`, ordered by id (certificates by fingerprint), `limit` 1 to 500 (100 by default); the cursor is opaque, null on the last page, and a page never repeats or skips an object that existed when the first was read. Errors are `{"error": {"code", "message", "fields"}}` with a stable code: `unauthorized` (401, with `WWW-Authenticate`), `forbidden` (403), `not_found`, `invalid` (400, `fields` per field), `conflict` (409: the target or watch exists, the finding is resolved), `rate_limited` (429, with `Retry-After`), `unsupported_media_type`, `too_large` (the body is limited to 1 MB), `node_offline`, `timeout`, `poll_failed`, `delivery_failed`, `unavailable` (a restore is running) and `internal`.

Every endpoint goes through the same role × action decision as the UI, with the token's role in force; the negative test suite tries every endpoint with every role's token, without a token and with an admin's session cookie. Each token is limited to 10 requests a second with bursts of 100; an address that presents 20 invalid tokens is refused for a while, regaining one attempt every 30 seconds, with a valid token too. Every write through a token is in the audit log under the token's user, with `token="name"` in the details; an acknowledgement through a token is by "Name (token name)".

## Architecture

One Go binary, one SQLite file, no other services. The frontend is server-rendered with `html/template` and embedded in the binary together with the CSS, fonts and compiled TypeScript; the scheduler and alert dispatcher run as goroutines in the same process.

```
 Browser ◄──► ┌─────────────────────────────────────────────────┐
              │ One Go binary                                   │
              │                                                 │
              │  Web UI + JSON API       Scheduler              │
              │  templates, TypeScript   daily, jitter, pool    │
              │                               │                 │
 OIDC    ◄─── │  Authentication          Prober ──────────────► │ ──► Targets
 providers    │  local, TOTP, OIDC       TLS, STARTTLS, chains  │     (TLS endpoints)
              │        ┌───────────────────────┘                │
              │        ▼                                        │
              │  Checker ───────────────► Notifier ───────────► │ ──► SMTP relay,
              │  findings, thresholds     outbox, retries       │     Telegram
              │                                                 │
              │  ┌───────────────────────────────────────────┐  │
              │  │ SQLite, one file: targets, certificates,  │  │
              │  │ observations, findings, outbox, users     │  │
              │  └───────────────────────────────────────────┘  │
              └─────────────────────────────────────────────────┘
```

The scheduler hands targets to the prober, the checker turns each observation into findings, and the notifier delivers them; every component reads and writes the one SQLite file, and the web UI shows what is in it.

**Backend layout**:

| Package | Responsibility |
| --- | --- |
| `cmd/tlswatch` | main; subcommands `serve`, `create-admin`, `migrate`, `backup`, `check` (one-off probe of a host, prints JSON, exit code by severity) |
| `internal/probe` | TLS and STARTTLS dialers, chain capture, verification against system store or bundle, the pinned handshakes of the configuration test (legacy versions and suite classes); no database access, so the node reuses it unchanged |
| `internal/node` | The agent protocol: job and result messages, the server-side dispatcher and `/agent/v1` handlers, and the node client loop run by `tlswatch node`; transport behind an interface |
| `internal/check` | Turns an observation into findings: thresholds, change detection, debounce; the grade rules as a versioned table |
| `internal/ct` | Certificate Transparency: the source interface with the Cert Spotter and crt.sh clients, the hourly poller, issuance matching by issuer and serial, and the pending hold |
| `internal/core` | Domain: targets, certificates, findings, acknowledgements, state transitions; the YAML export and the import plan |
| `internal/sched` | Scheduler: per-target next-run with jitter, worker pool, Check now queue |
| `internal/notify` | Channels, message rendering, outbox with retry |
| `internal/auth`, `internal/authz` | Passwords, TOTP and recovery codes, sessions, OpenID Connect (Google and generic); the role × action decision |
| `internal/qr` | The QR code encoder that draws the TOTP setup code as SVG |
| `internal/db` | SQLite access and embedded migrations, run at start; online backup and in-place restore |
| `internal/backup` | The encrypted backup file of the UI: writing it, and checking, migrating and re-sealing an upload before it is restored |
| `internal/web` | HTTP handlers, pages, the internal JSON API under `/api/v1` used by the TypeScript (check, check all, test probe, finding panel, change stamp), and the public REST API under `/api/v2` with its OpenAPI document |
| `web/` | templates, `static/css`, self-hosted fonts, `ts/` sources compiled to `static/js` |

**Database**: SQLite in WAL mode through `modernc.org/sqlite` (pure Go, so the binary is static and cross-compiles without cgo). One writer goroutine serialises writes; reads are concurrent. Certificates are stored once by fingerprint with the PEM; observations reference them. Expected size at 100 targets with daily checks and 180 days retention: under 50 MB.

**Backup and restore**: the UI backup (Settings › Backup) is a `VACUUM INTO` copy in a temporary directory next to the database, in a tar archive with a manifest (format, tlswatch version, schema, time), encrypted as a stream of 64 KiB AES-256-GCM chunks under a key derived from the passphrase with Argon2id (64 MiB, 3 passes; parameters and salt in the file header). Since the file chooses its own cost and the setup screen takes an upload before anyone signs in, a file asking for more than 256 MiB, 8 passes or 4 threads is refused before a key is derived. The chunk counter is the nonce and the header and a last-chunk flag are the additional data, so a wrong passphrase, an altered file and a cut-off download all fail, as does a file with data after its last chunk. Inside the copy, channel credentials and the Google client secret are re-sealed from the instance key under a second key derived from the passphrase: the file restores on any instance, and the instance key never leaves the server. An upload (1 GB at most, read as a stream, so nothing is buffered in memory or spilled to /tmp) is written to a temporary directory, checked (`integrity_check`, a tlswatch schema no newer than the binary, at least one enabled admin), migrated, its credentials re-sealed under the instance key, and its sessions, one-time links and API tokens deleted (a token revoked since the backup would otherwise work again). Then the scheduler stops starting checks and housekeeping and waits for the running ones, the outbox waits for a running delivery (the node dispatcher pauses first and drops its queued and leased jobs, so the node checks end at once), and SQLite's backup API copies the file over the live database through the writer connection in one step; readers see the old database or the new one. The settings and CA bundle caches and the remembered sign-in addresses are dropped, the schedule is rebuilt as at startup, and the restore is written to the restored audit log. Everyone is signed out and signs in again with an account from the backup. A plain database copy from the `backup` subcommand restores the same way without a passphrase; its credentials are assumed to be sealed under this instance's key, and a channel that cannot be decrypted is marked as after a lost key.

**Retention**: observations, findings, alert log and audit entries older than 180 days (configurable) are pruned hourly; a cached CRL no served leaf has named for 7 days is pruned with them. Certificates are kept while any observation references them. The current state of every target is always kept regardless of age.

**Scale**: the schedule is a priority queue by next-run time, so 10,000 targets cost memory, not CPU, between runs. Probing is bounded by the worker pool; SQLite handles the write rate of daily checks on thousands of targets with margin. The single-process design is a deliberate limit: one instance, scaled up, not out.

**Dependencies** (Go): standard library, `modernc.org/sqlite`, `golang.org/x/crypto` (Argon2id), `golang.org/x/oauth2`, `go.yaml.in/yaml/v3` (the export document: the standard library has no YAML, and a parser of our own for a format people edit by hand would be the riskier choice). Nothing else without a reason written in the pull request.

## Frontend

The frontend is pages rendered server-side with Go `html/template`, and TypeScript only where a page cannot work as a plain form. Every page works without JavaScript; the API endpoints answer JSON to the TypeScript and a redirect to a form.

**TypeScript without dependencies.** `tsc` alone compiles `web/ts` to plain ES modules in `web/static/js`, loaded with `<script type="module">`. No bundler, no framework, no runtime package. The dev dependency tree is `typescript` only, enforced in CI by a `check-deps` script. The `tsconfig.json` settings: ES2022, `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`.

Where TypeScript is used in version 1:

- The target form's Test button (probe without saving, render the result), and the port following the protocol.
- Check now and Check all, with the row updating in place when the probe returns.
- Live pages: polling the change stamp and swapping in a fresh render (see Inventory and user interface).
- Clickable rows, table row expand/collapse, copy-to-clipboard for fingerprints and PEM, filter chips, and tags that act as chips.
- The acknowledge panel (until-date, comment, close with Escape), and the bulk selection on the findings and targets lists.
- Live filtering on the targets, certificates and findings tables, the "/" shortcut (shown as a key hint in the filter field), and links that carry the current filter.
- Column sorting on the targets table requests a globally sorted database page; certificates and findings re-order their rendered rows from `data-sort-*` values. All three keep `sort` and `dir` in the URL.
- Confirmation before deleting, and disabling a form's buttons while it is sent.

Everything else is a form, and every one of these works as a plain link or form without JavaScript (the bulk bar shows through CSS alone). Shared helpers (`$`, `api()`, `ApiError`, `onReady`) live in `common.ts`; error messages come from one `messages` map, in English.

**Styling** follows the design canvas (`design/` in the repository), which is an operations console, not a workflow portal. The rules: colour carries status and nothing else — green, amber, red and grey mean healthy, warning, critical and off, and appear nowhere else; actions use one neutral accent (slate blue); the chrome is a 48 px dark graphite bar with live counts in the navigation; content is light by default with a full dark token set, the theme chosen as in Share (system preference, manual override stored server-side in a cookie, no flash). Type is IBM Plex Sans at 13 px for the UI and IBM Plex Mono for host:port, fingerprints, serials, dates and counts, both self-hosted under their OFL licences. Every page is at most 1680 px wide; forms are at most 760 px wide whatever the page, filter fields 300 px, lifetime bars in lists 110 px, and an empty state with a title is centred. Lists are dense: 8 px row padding, uppercase 11 px column heads, status as a dot plus a word, a lifetime bar per certificate showing the share of validity already used, filter chips with counts instead of dropdowns, sorted by expiry by default. Notices are bars, not toasts; the acknowledge form is a side panel, not a modal. All colours are CSS custom properties on `:root`; no colour is hard-coded below the token blocks. The token values are listed in `design/README.md`.

**Wordmark.** An inline-SVG shield-with-check mark in the accent colour next to "tlswatch" in Plex Sans 600, 15 px in the bar and 22 px on the sign-in card. No company branding anywhere in the open-source project.

**Principles**: server-rendered pages with small TypeScript modules, light and dark from day one via tokens, real forms that work without JavaScript, notices as bars, the mono convention for identifiers, tables that fall back to cards below 760 px, and the `tsc`-only toolchain.

**Build and test tooling**: `npm ci && npx tsc -p tsconfig.json` to build; `node --test web/test/*.test.mjs` on the compiled output for the few pure functions worth testing (days-left truncation, fingerprint formatting, tag parsing); Go `testing` with `-race` for everything else, including handler tests against an in-memory SQLite. No test framework beyond what Node and Go ship.

## Configuration, deployment and operations

**Everything is configured in the UI, as far as possible.** Only what the process needs before it can open its database stays outside it: the listen address, the database path and the secret key. All the rest lives in the database and is edited under Settings by an admin: the SMTP relays (host, port, encryption, username, password, sender, recipients), the Telegram bot token and chat IDs, the Slack, Discord and webhook URLs, the ntfy server and topic, Google sign-in (client ID, client secret, Workspace domain), the OpenID Connect provider and the TOTP requirement, the public base URL, probe concurrency, retention, proxy trust and local-target policy, thresholds and the digest.

Secrets entered in the UI (SMTP passwords, Telegram bot tokens, Slack, Discord and Teams webhook URLs, Matrix and ntfy access tokens, PagerDuty integration keys, webhook signing secrets, the Google and OpenID Connect client secrets) are stored encrypted with AES-256-GCM under the secret key. They are never shown back; a password field left empty keeps the stored value. A copy of the database alone does not leak them. The `rotate-key` subcommand re-encrypts them under a new key while the server is stopped.

**Zero-configuration start.** `tlswatch serve` with no environment works. The data directory is created. A 32-byte secret key is generated into `data/secret.key` (mode 0600) when no key file exists. When no users exist yet, the server shows a setup screen at the first visit where the first admin creates their account and password; the log prints the URL. Because the default bind is loopback, nobody else can reach that screen before the admin exists. `create-admin` remains for scripted installs.

**Environment variables are optional overrides**, for container and GitOps deployments. A setting supplied by the environment wins over the database value and is shown in the UI as read-only with the note "set by environment". Saving the page leaves such a field's stored value as it is, so the environment's value never reaches the database or a backup, and removing the variable brings the stored value back. Values are validated like the UI fields; an invalid one stops startup with a message naming the variable (except `TZ`, which is ignored when unknown). The same holds for the bootstrap variables and on a node. A boolean takes `true`/`false`, `1`/`0` and `yes`/`no`.

| `TLSWATCH_WORKERS` | `8` | Settings › Defaults | Concurrent probes |
| `TLSWATCH_RETENTION_DAYS` | `180` | Settings › Defaults | History retention; the audit log is kept at least a year regardless |
| `TLSWATCH_GOOGLE_CLIENT_ID` / `_SECRET_FILE` / `_DOMAIN` | empty | Settings › Sign-in | Google sign-in; off while no client ID is set |

Settings pages added for this: **General** (base URL, proxy trust, local targets, metrics) and **Sign-in** (Google client ID, secret, domain, with the redirect URI to register shown read-only; later the OpenID Connect provider and the TOTP requirement). Channels gain the SMTP encryption choice (STARTTLS, implicit TLS, none) and username/password as in the mockup; Telegram channels take the bot token and one or more chat IDs. Slack, Discord, ntfy and Webhook channels (added later, not in the mockups) follow the same form layout with their own fields. Every change is audited, secrets redacted.

**Packaging**: `go build` produces one static binary with the frontend embedded via `embed`; releases ship binaries for linux/amd64, linux/arm64, linux/arm (32-bit ARMv7, named after `GOARCH` alone because that is what a node asks for), darwin/amd64 and darwin/arm64, plus a Docker image from `scratch` with CA certificates for linux/amd64, linux/arm64 and linux/arm/v7, published to GitHub Container Registry. The image's build stages run on the builder's platform and cross-compile, so a multi-platform build does not run Go under emulation. The compose file in the repository runs the image with one volume for `data/`; TLS termination is left to the user's proxy.

**Subcommands**: `serve`, `create-admin -email`, `migrate` (also runs at start), `backup <path>` (SQLite `VACUUM INTO`, safe while running, never migrates), `healthcheck` (for the container), `rotate-key` (re-encrypts stored secrets under a new key; server stopped), `check <host[:port]> [-protocol -servername -ca-file -insecure -no-legacy]` for scripts and CI, exit code 0/1/2 by severity. It tests SSL 3.0, TLS 1.0 and 1.1 unless `-no-legacy` is given; each address in the JSON lists the old versions it accepted under `legacy_accepted`, absent when untested or without a verdict, the weak suite classes under `weak_suites_accepted`, its DHE group size under `dh_group_bits`, and the other certificates it serves under `other_certificates` (via `other_key` or `no_sni`, key type, subject, SHA-256, expiry and the checks each fails). `node [-server -data -workers -allow -allow-local -token -insecure]` runs the binary as a probe node inside another network, `node enrol -server -token` exchanges an install token for the credential, and `node uninstall` removes what the install script put in place (see Nodes).

**Operations**: `/healthz` reports database reachability and scheduler progress (last run, backlog, how long the oldest due check has waited); when enabled under Settings › General, `/metrics` serves Prometheus gauges to the bearer token generated there, since they name every target (targets by status, open findings by severity, alerts pending and given up, each target's certificate expiry, scheduler backlog and checks, checks running on nodes and targets held; nodes online and offline, seconds since each node was seen, jobs completed and failed per node); structured logs with request IDs and one line per check; a daily backup is the `backup` subcommand on a cron, and Settings › Backup downloads and restores an encrypted backup of the whole instance. Upgrades are a binary swap; migrations are forward-only and refuse to run a database written by a newer version.

**Development**: `make build`, `make test`, `make frontend`, `make run` with a throw-away database. There is no seed subcommand: test data does not ship in the binary. Demo data is a file outside it too (`demo/demo.json`, read in demo mode); a test loads that file, so it keeps working. The README screenshot shows letsencrypt.org and the badssl.com hosts (expired, self-signed, wrong host, untrusted root, tls-v1-0.badssl.com:1010), added through the UI.

## Security

The tool holds a list of hosts, their certificates (public data) and the credentials of its own alert channels. The risks are the UI being reached by the wrong people, the probe being used as a scanner from inside the network, and the alert credentials leaking.

- **Transport**: the binary listens on loopback by default and expects a reverse proxy for TLS; `BEHIND_PROXY` must be set explicitly before forwarded headers are trusted. HSTS (with subdomains) and `Secure`, `__Host-`-prefixed cookies when the base URL is https, every cookie `HttpOnly; SameSite=Lax`; before the base URL or proxy trust is set, a peer on a loopback or private address saying `X-Forwarded-Proto: https` is believed about the scheme alone, so a fresh install behind a TLS proxy gets Secure cookies from its first sign-in. Redirects after sign-in go only to a parsed, normalised path on this origin.
- **Headers**: `Content-Security-Policy: default-src 'self'` with no inline scripts or styles (all CSS in `app.css`, all JS in modules), `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `frame-ancestors 'none'`, `Permissions-Policy` denying camera, microphone, location, payment and USB, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`, and `X-Robots-Tag: noindex, nofollow`, so no instance, nor its sign-in page, turns up in search results.
- **API tokens**: bearer tokens for `/api/v2` only, hashed at rest, capped at their user's role, rate limited, and never accepted by the UI; the session cookie is not read under `/api/v2`, so a browser cannot be made to call the API with its user's rights. See Users above and REST API.
- **Sessions and CSRF**: as in Users above; one CSRF token per session, checked on every POST and on every JSON call via the `X-CSRF-Token` header, and a browser's cross-site request (`Sec-Fetch-Site: cross-site`) refused outright. The setup form answers "already set up" before it hashes a password, so it costs nothing to post at once setup is done.
- **Passwords**: Argon2id, 12-character minimum, leaked-password list, rate limit per account and per IP; TOTP codes share that limit.
- **Probe as scanner**: only operators and admins can add targets, and every addition is in the audit log. Targets are probed with one TLS handshake and no application traffic beyond the STARTTLS preamble. Loopback and link-local addresses are refused as targets unless Settings › General allows them (`TLSWATCH_ALLOW_LOCAL=true` pins that); private ranges are allowed because monitoring internal addresses is the point.
- **Secrets at rest**: channel credentials, the Google and OpenID Connect client secrets, the Cert Spotter API key, unspent node install tokens and TOTP secrets are encrypted with AES-256-GCM under the secret key file, each bound to its place (table and column, or settings key) as additional data, so a sealed value moved to another row or column does not open; the key is never in the database or in a backup, and a key rotation or a restore re-seals all of them (values sealed by older builds, without a place, still open and are re-sealed then). A TOTP secret the old key cannot open is dropped with its recovery codes, and `rotate-key` names the users, who sign in with their password and set TOTP up again. A sealed setting the key cannot open is shown as unreadable where it is entered, never silently empty. A server whose key file is missing while its database holds sealed credentials refuses to start (a mis-mounted volume, not a first start) unless `TLSWATCH_ACCEPT_NEW_KEY=true`. The database, its copies and the key file are created owner-only. Logs redact tokens and passwords.
- **Outbound connections** are limited to the targets, the SMTP server, `api.telegram.org`, the Slack, Discord, Teams, Matrix, ntfy and webhook URLs an admin configured, PagerDuty's Events API (followed to no redirect, and posted with Discord mentions off), the Certificate Transparency source chosen under Settings (`api.certspotter.com` or `crt.sh`, which receive the watched domain names), the system's name servers for the CAA lookups of watched domains, the CRL distribution points of served certificates, which the CAs name in the certificates themselves (fetched without credentials, redirected only to `http://` or `https://`, 30 seconds at most, 50 MB at most), Google's OIDC endpoints and those of the OpenID Connect provider an admin configured (discovery, token and userinfo), and, on a release build, the signed release checksums on GitHub when a node downloads a binary. No telemetry, no update check.
- **Nodes**: a node makes outbound HTTPS connections to the server only and is never connected to; it sends back hostnames, chains and handshake metadata and nothing else. Its credential is stored hashed on the server and in a 0600 file on the node; the agent endpoints take that bearer credential only and are rate limited. A node-side allowlist of CIDRs bounds what a server can make it probe, and a node replaces its binary only with a release signed by the release key, so a server cannot make it run anything else. See Nodes.
- **Input**: hostnames validated as DNS names or IP literals, ports 1 to 65535, PEM bundles parsed and rejected when they contain private keys, tags limited to 40 characters.
- **Untrusted bytes**: every parser of bytes a server or a remote service controls has a Go fuzz target: the STARTTLS dialogues of all five protocols, the record-layer reader and the ServerHello, ServerKeyExchange and SSL 3.0 parsers of the hand-built hellos, the must-staple extension, the stapled OCSP response, the embedded SCT list, the CRL and its issuing distribution point, the CAA answer, the CT sources' distinguished names, times and certificates, and the OpenID Connect ID token. Each is held to not panicking, not looping and staying inside its bounds, and the readers to their limits on line length, lines per reply and bytes per handshake.
- **Backups**: a UI backup holds everything, including password hashes and the alert credentials, so it is encrypted with the admin's passphrase; downloads and restores are in the audit log. A restore needs the admin role, or happens on the setup screen while no account exists, with the same trust as creating the first admin there.
- **Audit log**: every change to targets (also through an API token, which is named, or an import), API tokens made and revoked, users (including unlocks, deletions, TOTP set up, turned off or reset, new recovery codes, a recovery code used to sign in, and users created or given another role by an OpenID Connect role claim), channels, bundles, defaults, backup downloads and restores, and every acknowledgement (bulk ones marked as such), with user and timestamp; readable by admins, exportable as CSV, kept for at least a year whatever the history retention.
- **Supply chain**: Go dependencies pinned in `go.sum`, `govulncheck` and `gosec` (pinned versions) in CI, the npm tree limited to `typescript`, GitHub Actions and base images pinned by digest, each release job holding only the scope it needs, releases built in CI from a tagged commit with checksums published and signed (see Nodes › Updating nodes).
- **Metrics**: `/metrics` names every target and its weaknesses, so it is served only to the bearer token generated under Settings › General.

## Open source: repository, licence, CI, versioning

The project lives in a public repository under a personal GitHub account; company-specific material (logos, customer names, internal addresses) never enters it.

**Licence**: MIT. It is the shortest, matches Go and TypeScript community norms, and the tool has no patent surface that would argue for Apache-2.0. The fonts carry their own OFL licence files in `web/static/fonts`.

**Repository layout**

```
cmd/tlswatch/        main and subcommands
internal/...         packages as in Architecture
web/                 templates, css, fonts, ts, test
docs/                this specification, operations guide
design/              design canvas: README with tokens, mockups/*.dc.html
.github/workflows/   ci.yml, release.yml
Dockerfile, compose.yaml, Makefile, go.mod, package.json, tsconfig.json
LICENSE, README.md, CONTRIBUTING.md, SECURITY.md, CHANGELOG.md
```

**CI** on GitHub Actions:

1. Frontend: `npm ci`, `npm audit --audit-level=low`, `check-deps` (typescript only), `tsc`, `node --test`.
2. Backend: `gofmt -l`, `go vet`, `go test -race ./...`, `govulncheck`, `gosec`. The fuzz targets' seed corpora run as part of `go test`; `go test -fuzz=<target>` in a package runs one for longer.
3. Build: binaries for the three platforms and the Docker image, pushed to `ghcr.io` on a tag. The release workflow runs the same frontend and backend jobs on the tagged commit first and publishes nothing when they fail; the release notes are generated from the commits since the previous tag. A `v0.0.x` tag is a test release: marked as a prerelease and not moving the image's `latest` tag.
4. Renovate or Dependabot for pinned dependencies and action digests.

**Versioning**: semantic versions from `v0.1.0`; `v1.0.0` when the scope in this document is complete and the database schema is considered stable. `CHANGELOG.md` kept by hand, one line per change, newest first.

Nobody chooses a version for a build by hand. `scripts/version.sh` derives it from the checkout, and the Makefile and the Dockerfile both use it, so `make build` and `docker compose up --build` report the same thing: the tag when built exactly on one (`v0.2.0`), the tag with the distance and hash past it (`v0.2.0-5-g5efacf7`), and while no tag exists the commit date and hash (`2026.10.15-5efacf7`); `-dirty` is appended when the working tree had uncommitted changes, and `dev` is the fallback outside a git checkout. The release workflow passes the tag explicitly. The `.git` directory is in the Docker build context for this. A build without a release tag is a development build: its static files are not cached for good, and it does not update nodes automatically (see Updating nodes).

**Community files**: README with a screenshot, a three-command quick start and the `check` one-liner; CONTRIBUTING with the dependency rule (no new runtime dependency without a written reason in the pull request) and the test expectation; SECURITY with a private reporting address; issue templates for bug and feature; the specification itself in `docs/` so decisions are traceable.

**Name**: tlswatch. Candidates checked and rejected: `certlens` and `certscope` are taken (a Python package and a Firefox extension), `certwatch` is CertLight's former name, `certview` is a Qualys product. Check the GitHub name, the Go module path and Docker Hub before the first release.

## Planned after version 1

The features below were adopted on 17 October 2026 after a review of comparable tools. Each one is specified here so it can be built as written, and its text moves into the sections above in the same change that ships it; the numbers stay as adopted. Number 1, lifetime-relative thresholds and `renewal_overdue`, is built and described under Checks and Thresholds and defaults; number 2, the distrust calendar, under Checks; number 3, discovery, under Discovery; number 4, revocation through CRLs, under Checks (Revocation); number 6, the field-level diff on `certificate_changed`, under Checks (Change detection); number 7, CAA monitoring, under Certificate Transparency watching (CAA); number 8, post-quantum key exchange, under TLS configuration grade; number 9, more channels and the expiry calendar, under Alerting; number 10, TOTP and generic OpenID Connect, under Users, authentication and authorisation; number 5, the REST API and import/export, under REST API, Users, authentication and authorisation (API tokens) and Inventory and user interface (Export and import). All ten are built. They were listed in the order of building, by value against effort. Most of them exist to make tlswatch stand out, not to catch up: they make it the independent check that a team's renewal automation actually deployed its certificate, at a size and price nobody else covers.

### Left out on purpose

Status pages, login and uptime checks, SSH banners, and certificates read from files, keystores or Kubernetes secrets are not planned. They would widen the tool into what Uptime Kuma, Gatus and the Prometheus exporters already are. "It only observes what is served" is the reason to pick tlswatch over them.

## Decisions taken, assumptions and open points

Where the requirements said "not sure" or "what do you recommend", this document takes a position. The table records why, so a later change knows what it reverses.

| Topic | Decision in this document | Why |
| --- | --- | --- |
| Legacy TLS versions | Test SSL 3.0 (with a hand-built ClientHello), TLS 1.0 and 1.1 once a day per address; `legacy_protocol` warning; per-target switch to turn it off | Compliance baselines (PCI DSS, NCSC, BSI) require them off, and a firmware update or a reset load balancer profile can turn them back on unnoticed; daily is enough for a setting that rarely changes, and the switch keeps unfixable appliances from becoming noise |
| Multiple A/AAAA records | Probe all addresses, up to 8; `inconsistent` finding when they differ; per-target switch to first-only | The one stale node behind a load balancer is the failure a single probe misses |
| Grouping | Free-form tags plus a notes field, no fixed hierarchy | Enough at 100 targets; a hierarchy adds screens and migrations |
| Alert behaviour | Transition alerts, severity-based reminders, recovery notices, acknowledge with snooze, optional weekly digest | Daily checks must not become daily mail |
| Severities | Three: info, warning, critical | Four levels invite routing rules nobody maintains |
| Change detection | `renewal managed` flag per target, auto-set for known ACME issuers | Let's Encrypt churn would otherwise drown real changes |
| Frontend | Server-rendered templates plus small TypeScript modules, not a single-page app; the look is an operations console (status-only colour, dense lists, overview home), not a workflow-portal style | Smallest dependency footprint; a workflow-portal style does not fit a monitor |
| Tooling | `tsc` only, `node --test`, Go `testing`, GitHub Actions, Renovate | Small, standard and reproducible |
| SQLite driver | `modernc.org/sqlite` (pure Go) | Static binary, cross-compiles without cgo |
| Licence | MIT | Simplest; no patent concern |
| Internal networks | A node inside the network, the same binary as the server; the probe package is database-free so the node runs it unchanged (see Nodes) | One inventory and one binary; a second instance would split the inventory, users and alert rules |
| Node: who schedules | The server owns the schedule, the data and the checks; the node is stateless apart from its credential and runs one probe at a time per worker | One inventory and one schedule; a node holds nothing worth backing up or losing |
| Node: transport | Outbound HTTPS long-poll with a 55 s ceiling; no WebSocket | The node is never connected to, so one outbound firewall rule suffices; a held request delivers a job within one round trip; no dependency, no proxy upgrade configuration, and on a link carrying one job every half hour a socket would buy nothing |
| Node: trust | CA bundles stay on the server, which verifies `bundle` chains itself; `system` uses the node's host store; the node's own connection to the server uses the host store too | Trust is managed in one place; a changed bundle needs no node update; the node cannot receive a CA from a server it does not yet trust |
| Node: install | One command from the UI, a script served by the instance with a one-time token in its URL; the admin confirms the reported hostname and addresses before the node can take targets | No keys made by hand; a token in shell history is harmless because an unconfirmed node is inert and a stranger's machine is rejected on sight |
| Node: binary source | The server serves its own executable for its own platform, redirects to its release asset otherwise | Node and server are always the same version; a same-architecture network needs no internet |
| Node: updates | Automatic by default, converging on the server's version in both directions, one node at a time, rollback after five minutes without a poll; containers are pulled, not patched; `dev` builds update by hand | Nobody logs in to a node; a bad release reaches one network before it reaches the rest; a replaced binary in a container would be lost on restart |
| Node: binary ownership | The binary belongs to the node's user, under its data directory, with `NoNewPrivileges` | Self-update needs a writable binary; a compromise of that user already runs code as that user, so this adds no privilege |
| Node: offline | Targets keep their state and show "Waiting for node"; one `node_offline` finding per node after 10 minutes, critical once a target is overdue | A dead node is one problem, not fifty unreachable hosts |
| TLS grade: four grades, rules in a versioned table | A, B, C, F from pinned handshakes per suite class, the lowest address counts, every grade carries its reasons; no A+ and no D; certificate validity stays out of the grade | A letter sorts a list and settles a discussion with a vendor; finer steps invite arguments about scoring; a grade without reasons is a verdict nobody can act on; an expired certificate already has a critical finding and must not be counted twice |
| TLS grade: one finding per cause | Versions stay `legacy_protocol`, signature and key size stay `weak_signature`, suite classes get `weak_configuration`; B-grade causes open no finding | Nothing alerts twice for one fix; CBC and a missing TLS 1.3 are worth a column, not a page |
| CT: an index, not the logs | Issuances come from Cert Spotter or crt.sh through a source interface, polled hourly per domain from the server | Tailing the logs is a service in itself; an interface keeps the choice open, including a self-hosted index |
| CT: match by issuer and serial, hold renewals 48 hours | A precertificate has no usable fingerprint; an issuance whose names and issuer match a target waits 48 hours before it is unexpected | ACME renewals appear in the logs hours before they are deployed and must show up as one quiet line, not as a warning followed by a recovery |
| CT: watches are explicit | Operators add domains; nothing is derived from targets; the first poll's backlog opens no finding | A target on a customer's host does not make that domain yours; a new watch must not open fifty findings on day one |
| Expiry: lifetime-relative | Thresholds in days and as a share of the lifetime, the later of the two deciding; `renewal_overdue` past 75 % on renewal-managed targets | Days alone fire at issuance on a 6-day certificate and a share alone months ahead on a 1-year one; the failure to catch is a renewal that never deployed |
| Distrust: a table in the binary | Root-program distrust events as a versioned table of roots (by key), dates and rules; only the anchor counts, and not when the program's own roots offer another path; `distrusted_ca` warning before the date, critical after; Chrome's rolling cutoffs on replaced roots left out | Distrust is announced months ahead and fails silently in one browser; a table needs no runtime fetch and nodes need no update; flagging every cross-sign an old root left behind would cry wolf on the largest CAs |
| Revocation: CRL first | Daily CRL fetch per distribution point, `revoked` critical; OCSP stapling shown, never required; OCSP queries only for private CAs later | Public CAs are dropping OCSP; "no OCSP URL" is normal, not a finding |
| Must-staple: critical, asked twice | A must-staple leaf without a good staple is critical on every check; the probe asks again after 2 seconds before reporting | Firefox refuses the connection, so it is an outage for some users; lazy stapling after a restart would otherwise page someone for a staple that arrives a second later |
| Other certificates: the alternate alerts, the default does not | The certificate served by key type is held to every certificate check and alerted; the one served without SNI only to being valid, as info | Clients that get the alternate are real and many; clients without SNI are few, and a default certificate for another name is normal on shared hosting |
| Discovery: offered, never monitored | Network scans from a node and names from CT produce a list to tick, which goes through Add many; private ranges only by default | Discovery feeds the inventory without silently widening what is monitored or turning nodes into scanners |
| TOTP: second factor for local accounts only | RFC 6238 with the app defaults, QR drawn by our own encoder, 10 hashed recovery codes, required per role, codes counted with the password lockout | Every authenticator app reads the defaults; a QR library would be the only dependency for one picture; a single sign-on account's second factor is its provider's; counting codes with passwords keeps one limit an attacker with the password cannot reset |
| SSO: one generic OpenID Connect provider, Google a preset of it | Discovery, PKCE, no signature check on the ID token from the token endpoint, userinfo fallback, optional role claim that decides the role at every sign-in | One implementation covers Entra ID, Keycloak, Authentik and Okta; TLS to the token endpoint vouches for the token (OIDC Core 3.1.3.7) so no JWKS cache is needed; the identity provider is where group membership is managed, so it should decide the role; SAML is left out |
| Public API authentication | Personal API tokens as bearer tokens, capped at the user's role, under `/api/v2` only; no session cookie there, no OAuth client flow | Scripts and CI need a credential that is not a browser session; keeping the two apart removes CSRF from the API and keeps a stolen token out of the UI |
| API updates | `PATCH` with the fields sent, `null` resetting an override; lists by cursor in id order | Partial updates fit scripts that change one setting; an id cursor stays stable while targets are added |
| Export format | YAML with only non-default settings, names instead of ids, one document for targets and watches, imported through Add many with a preview | Readable and diffable in a repository; names survive a move to another instance; the preview makes a round trip safe, and nothing is deleted unless asked |
| Scope: what stays out | No status pages, uptime or login checks, SSH, or certificates from files, keystores or Kubernetes secrets | Those are what Uptime Kuma, Gatus and the exporters already do; observing what is served is the reason to pick this tool |

**Assumptions**

- The tool runs on a host that can reach the public internet and the internal addresses it monitors.
- A reverse proxy handles TLS for the UI itself.
- E-mail goes through an SMTP relay that already exists; the tool is not a mail server.
- The fonts are OFL and can be redistributed with an MIT-licensed project.

**Open points settled.** The questions the first draft left open were decided on 16 October 2026 and are recorded in the sections above: MIT as the licence; all addresses as the default; TOTP as a later version; `info` findings outside the weekly digest; and letsencrypt.org plus the badssl.com hosts as the screenshot data. No open point remains for version 1.

**Later versions**: a self-hosted Certificate Transparency index as a third source; a stricter grade rule set (TLS 1.2 without 1.3 to C, post-quantum key exchange gating A) once the installed base allows it; OCSP queries for private CAs; ticket creation in a service desk on critical findings.
